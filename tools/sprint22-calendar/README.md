# Проверка календарного этапа Sprint22

Продукт меняет только два сообщения в таблице рабочей длительности. Свидетельства относятся к двум синтетическим журналам и фиксированным ручным примерам Europe/Berlin, а не ко всем календарям или рабочим нагрузкам.

## Проверка скачанного пакета

Из корня скачанных исходников запустите Python 3 с изоляцией и отключённым кешем:

```text
python -I -B tools/sprint22-calendar/verify-package.py evidence/sprint22-calendar tools/sprint22-calendar <private-output>/calendar-package.json
```

Каталог `<private-output>` должен уже существовать, а файлы результата — отсутствовать. Проверяющий ограничивает пакет 150 файлами, 4 MiB и 200 узлами дерева, отклоняет символьные ссылки и Windows reparse points. Он проверяет манифест, хеши, размеры, отсутствие лишних файлов и очевидных секретов/машинных путей, сохранённые состояния браузера, статусы 422 и stdout тестов.

Затем в том же процессе исполняется `audit-calendar-proof02.py` с закреплённым SHA256. Он перечитывает все 60 ответов HTTP, параметры отправленных форм и исходные CSV: проверяет ручные 7 200 000 / 14 400 000 мс, отказы и сохранность настроек, сравнивает C01 и C02. Ожидаемые длительности не вычисляются тестируемым сервером. Дополнительный результат записывается рядом, с окончанием `.http.json`.

Снимки проверяются по хешам; чтение пикселей подтверждено отдельными решениями QA/Customer, а не этим скриптом. Сводка процессов содержит хеши частных оригиналов; только два указанных stdout опубликованы полностью. Это ограничение сохраняется и после успешного выполнения проверяющего.

## Повтор живой HTTP-проверки

`check-calendar-http02.py` предназначен для отдельного, уже запущенного локального тестового стенда на `127.0.0.1:3139` или `:3140`, с новой БД и изолированным каталогом результатов. Он создаёт тестовую учётную запись/проекты и импортирует два маленьких CSV. Это изменяет тестовый стенд; не запускайте его на рабочей установке.

Для C01 используются `--url`, `--output`, `--credentials`, `--candidate C01`; для C02 дополнительно `--baseline <C01-output>/proof.json`. Файл учётных данных хранится вне каталога публичных ответов и не публикуется. Оба сервера должны использовать одну тестовую БД с сохранённой сессией, последовательно на одном адресе. Бинарники, время жизни процессов, ресурсы и аварийное завершение контролирует внешний владелец стенда; сам HTTP-скрипт не заменяет этот контроль.

Скрипт HTTP не заявляет браузерную проверку. Браузерные свидетельства в пакете получены отдельным фактическим проходом Root. Прежняя неудачная попытка ожидала исходное имя `spring` вместо нормализованного `case-0`; её материалы сохранены отдельно, а версия02 исправляет только это ожидание, без изменения временных примеров.
