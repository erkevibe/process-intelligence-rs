## Пользовательские требования и приоритет

- S9-C01: прежде permanent delete оператор видит точное имя+UUID проекта, объём связанных журналов/моделей/папок/участников, последствия для источников и незавершённых jobs; явная отдельная destructive confirmation с привязкой к актуальной revision/плану. Архивирование с восстановлением и постоянное удаление имеют разные подписи и объяснения. Несовпавший/stale план отказывается, не расширяет удаление.
- S9-C02: permanent delete только owner, с реальными запретами editor/viewer/foreign/устаревшей session/currentrole. Определить заранее удаление текущего/последнего проекта и перенаправление всех sessions без неявного чужого проекта. Pending worker не может воскресить удалённые ресурсы. Удалённый UUID не повторно используется.
- S9-C03: безопасная recovery инструкция: до удаления проверенная backup/new restore; после удаления восстановление только в новый проект/DB с явной новой идентичностью, без обещания отмены одной кнопкой. Не обещать восстановление отсутствующего исторического raw. Если backup не обязательный product gate, явно обосновать это в exact plan и назвать необратимость без него; Customer предпочитает обязательный проверяемый backup для этой итерации.
- S9-C04: бизнес-аудит показывает actor/project/resource/action/policy/time/result для точного заранее перечисленного набора успешных действий, понятные русские подписи и полный export. Mutation+успешная запись атомарны; отказ и intent не обозначаются успехом. После permanent delete остаётся минимальное доказательство удаления в отдельном доступном бывшему owner контуре, без логов/raw/паролей/token/session/имён файлов или копии удалённых payload. Политика владения/retention/access заранее фиксируется, не общий административный доступ к чужим audit.
- S9-C05: bounded retention честно показывает сколько доступно/сколько утрачено, монотонный sequence и дату. Не называть512 последних действий полной compliance history. Проверить audit survivors после restart/delete и невозможность чтения/подмены чужим. Business policy version/result добавить явно, не угадывать по action string.
- S9-C06: cleanup CLI Preview объясняет, что создаёт новый verification restore, называет actual target identity, точные candidate keys/количество/логические bytes, archive/plan SHA, no-op/refusals. Apply требует exact plan confirmation; source/restore offline leases, реальные identities и полные values/versions/sequence. Не сжимает диск автоматически; PostgreSQL reuse и OS file shrink различны. Никакого startup/scheduled/HTTP cleanup.
- S9-C07: обязательны полный unreduced historical corpus, conservative отказ при unsupported/mismatch/active writer/alias/stale values и проверенная новая recovery. F01/F02/F03 нужны фактически на настоящем frozen CLI: beforeDELETE, наблюдённый afterDELETE-beforeCOMMIT, потеря наблюдённого успешного COMMIT response. HTTP303 loss не заменяет PostgreSQL ACK loss. Uncertain outcome → read-only complete PRE/POST reconciliation, никакого blind retry; unexpected state STOP.

Если cleanup native protocol fault или budgets не доказаны, оставить DISK01/R3-04 OPEN и исключить Apply из принимаемой возможности; не уменьшать corpus/timeouts ради PASS. ## Основание и риск

Current source показывает per-project audit last512 с total/dropped и owner access, archive сохраняет данные. Это полезная база, но удаление project не должно одновременно удалять единственное доказательство удаления или оставлять доступную payload копию в audit. Auth/repository/jobs/records cleanup должны быть одной доказанной транзакционной границей, иначе возможны orphan data, resurrected result и fake successful audit. Согласованный безопасный lifecycle delete нужен исходномуR3-01, а не добавляется как скрытое полное enterprise условие.

Предлагаю сначала ограниченный явный action ledger + permanent delete одного owner проекта с bounded backup/recovery/конкурентной publication защитой; cleanup параллельно как feasibility-first независимый CLI контур. Не начинать разрушительные user operations до готовых recovery и candidate gates. Основной риск proof capacity/native protocol interception, а не количество строк кода. Прежнее DISK01 design разумно отказывает unsupported state и честно различает hash domains; его большие corpus/F02/F03 не объявлять выполненными по чтению.

Эмоциональная перспектива предыдущего отдельного advisory сохраняет доверие через ясное «что останется/что исчезнет/как вернуть»; новый bounded запрос отправлен existing emotional_s7, ответ ещё не получен, не выдумывается и не является шестым голосом. Эта позиция не vote и не runtime/data action.
