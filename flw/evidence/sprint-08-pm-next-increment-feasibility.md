## Recommendation: choose only R2-C06 date/state listing, conditionally

This has a smaller finite surface than generic R3-02 and can remove an actual unmet original scenario. Existing stable `log-*` IDs already distinguish duplicate names; no new identity scheme is needed. Do not add lost-ACK durable operation-index work to this increment: that is a different R2-03 protocol and would defeat the time budget.

Current list obtains metadata-only resource summaries and renders filename/ID/events/links. StoredLog has no creation timestamp. Proposal for the smallest honest contract:

- Add optional `created_at: DateTime<Utc>` to stored log metadata, default absent/omitted for legacy. New results use server UTC at successful creation publication preparation; store in the same authoritative repository mutation. Clearly label it “saved/created in this application”, not event time, file modification or original historical import time. Preserve on edits, restart, backup/restore; restore preserves original historical field, does not stamp now. No timestamp inferred from log ID, analysis_version, filesystem or historical audit.
- All creation paths through the shared StoredLog insertion must set it; repository_v2 serialization, decoder and full backup retain it. Old missing value renders “дата неизвестна”. Malformed explicit dates refuse; unknown fields remain strict. UTC human display and machine RFC3339 value must agree. No hardcoded/dummy historical values.
- Display stableID, escaped filename, events and date for each row, and a precisely scoped state. Without loading/validating full heavy payload, do not label “healthy/verified” just because log_state exists. A truthful state is “сохранённый результат анализа; целостность проверяется при открытии”, with a concise explanatory note. If original state criterion requires actual integrity/computation status, derive the narrow persisted publication state with required record-key completeness checks or say “metadata record only”; agree this semantic before code. Pending/failed jobs belong a separate job list and must not masquerade as saved logs.
- Preserve metadata-only bounded list behavior and current RBAC. Same-name journals remain distinct; no heavy payload loading just to render dates. New0.6.1 candidate needs old-record decode and unsupported downgrade warning. No auto update to0.6 or protected installations.

Literal independent gates before a full C06 acceptance: two same-name imports with different IDs and observable UTC times within captured publication windows; row events/date/state/ID exact and HTML-escaped; open/export each links to its own result; actual restart preserves all fields; backup/newrestore preserves them and source/action bytes; legacy absent date explicitly unknown, malformed date fails closed/no writes, viewer/foreign deny and list does not load heavy allocations. Include both strictCSV/XES and preview/job publication paths or prove their shared insertion identity. All other seven scenario gates must still be independently accepted before full R2-04; C06 improvement alone is not aggregate PASS.

## Why R3-02 generic policy/result is a larger separate task

Original actor/project/resource/action/policy/time/result means enough real context to understand the committed business operation. An authorization enum/currentrole records *permission*, not the actual import/order/filter/calendar/model/organization policy; a repeated constant “committed” records success, but not the business result identity/revision where those matter. Adding these generic dummy fields would not justify fullR3-02 PASS.

A sufficient finite audit schema would define action-specific typed policy/result variants and cross-validate action/resources/revision and actual operation values at commit. Auth grant/revoke/archive need actual role/lifecycle transitions; import needs source/order/provenance-operation/policy identity; filtering/calendar/model/folder mutations need the effective values or stable integrity-bound snapshot/hash and resulting affected resource revisions. System job interruption needs its real recovery policy/state transition. Successful-only entries may explicitly record committed outcome; no failed-intent entry is asserted to be committed. Current authorization identity remains useful additional context, not replacement business policy.

Historical entries must remain unknown without retcon: versioned optional context supports “legacy policy/result unavailable”; absent pair is legacy, malformed partial new context or unsupported enum refuses. Export/restore cannot fabricate actor trust. Historical policy hashes require their exact retained payload binding; otherwise they are just unverifiable labels. New fields affect every append site in Auth and Repo, serde/validation/backups/default compatibility, retention/tamper semantics and current rights/atomic rollback. Each authoritative store remains separately atomic; no fictitious crossstore transaction.
