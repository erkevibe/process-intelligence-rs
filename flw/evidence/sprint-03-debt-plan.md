## Migration acceptance to include in exact council proposal

M01 (owner root/storage; QA independent): obtain exclusive migration/application lock before any schema write, including bootstrap adoption. Fresh schema and recognized unversioned0.2 pi_kv/sequence state have deterministic versioned adoption. Validate expected table columns/types/constraints/sequence and existing required documents; unexpected/future schema fails before DDL/document changes. Merely CREATE IF NOT EXISTS plus a version row is insufficient validation of arbitrary preexisting schema.

M02: choose one additive compatible migration. History records version and immutable migration checksum; applied versions/checksums agree, repeated startup is idempotent. DDL/data changes and version marker commit in one transaction. Inject a meaningful failure after mutation but before commit; verify schema/version/documents unchanged. A deliberately paused actual migration killed on an isolated PostgreSQL backend must leave either old or fully new valid state; no half version. Concurrent upgrade/startup must deny or wait with bound, not race caches/schema.

M03: upgrade a copied0.2 database containing users/roles/sessions/projects/logs/model revisions/current/views/completed and interrupted jobs. Verify IDs, full source/analysis/parameters/model exports/auth enforcement before and after. New version rejects unsupported future schema/checksum mismatch with honest reason. Old0.2 binary has no schema-version gate: do NOT claim it rejects a newer schema. Either prove the selected additive upgrade's bounded old read/write compatibility, or explicitly forward-only operational policy with preupgrade backup/restore; no universal downgrade guarantee.

M04: operational backup/recovery means a separate database-level backup preserving schema and auth, not project-export JSON which excludes accounts. Validate a complete isolated restore into a new data/database target before relying on backup; source cluster untouched. Record failure windows and tool versions. Never publish credentials/dumps/user data. A successful project restore alone is not PostgreSQL disaster recovery.

## Crash recovery and deadlines acceptance

R01 (owner root/Operations): fix bootstrap interruption between initdb and private config with privately staged credentials/config tied to that cluster; resume safely on matching partial state and refuse inconsistent/unknown state. Test targeted phases before initdb, after PG_VERSION and before config finalization on newly isolated clusters; preserve partial files/logs for diagnosis. Never regenerate/reset credentials or remove an existing live user cluster to obtain PASS. Cold nativePS5 public Start and role-exists/database-missing rerun remain regressions.

R02 (owner root/storage): explicit connection, statement and lock deadlines with bounded response and honest error. recv_timeout alone does not cancel a synchronous worker query or later commit; avoid announcing a rollback when lost commit acknowledgment makes outcome uncertain. Use actual long-running query/lock on isolated database and verify controlled failure, unchanged prior data where rollback is known, recovery/restart and no falsely successful publication. Uncertain commit outcome should require read/reconciliation, not blind non-idempotent retry.

R03: actual abrupt own-cluster PostgreSQL stop during deliberately controlled write transaction and after durable commit. Restart/WAL recovery verifies exactly old or committed complete project, no partial result/terminal-job mismatch, IDs and auth preserved. Application lease lost→cached reads fail closed; replacement startup acquires exclusive lock; existing worker cannot silently reconnect and reuse stale cached auth. Recheck singleton/current actor views and bounded jobs. PostgreSQL process ownership must be established by exact executable+data directory/port before stopping it.
