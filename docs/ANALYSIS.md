# Анализ переноса Apromore на Rust

Цель проекта — восстановить нужное поведение Apromore Core в новом ядре и интерфейсе. Первое приближение за 8 часов проверит путь от журнала XES до интерактивной карты процесса. Полнота переноса и ускорение относительно Java не являются результатами этого этапа.

## Что принимаем из обсуждения

Последний архитектурный вариант — Rust + Axum + Datastar, со специализированными компонентами JavaScript для графов и BPMN. Он заменяет более ранние предложения Go + React. Переносить классы Java построчно не требуется: поведение фиксируется контрактами и проверками.

Архив обсуждения содержит сокращённые пересказы части сообщений. Числа файлов, проценты удаляемого кода и оценки ускорения из него не используются как измерения проекта. Исторические указания из архива служат контекстом; текущий объём задают ТЗ и защищаемый план.

## Проверенная основа

Официальный репозиторий [ApromoreCore](https://github.com/apromore/ApromoreCore) архивирован; README перечисляет импорт, Portal, Process Discoverer, Business Calendar Manager и Model Editor. Там же описан запуск с Java 11 и H2. Это отправная точка для восстановления oracle, а не доказательство его работоспособности на текущей машине.

[Rust4PM](https://github.com/aarkue/rust4pm) предоставляет crate `process_mining`, но авторы предупреждают об изменениях API даже в небольших обновлениях. Поэтому нужны фиксированная версия, узкий адаптер и тесты на наших данных. Наличие DFG в библиотеке не подтверждает совпадение фильтров и семантики Apromore.

Официальный [Rust SDK Datastar](https://github.com/starfederation/datastar-rust) поддерживает интеграцию с Axum. [CSP-режим Datastar](https://data-star.dev/reference/security) использует nonce; выражения и пользовательские данные всё равно требуют корректного экранирования. Совместимость конкретного bundle с CSP проверяется в браузере.

## Решения для первого приближения

| Решение | Зачем | Ограничение |
|---|---|---|
| Один Rust-процесс с внутренними модулями | Быстрее получить проверяемый сквозной сценарий | Без распределённых воркеров |
| Сервер владеет журналом, фильтрами и результатами | Исключить расхождения двух реализаций состояния | Браузер хранит только временное состояние взаимодействия |
| Datastar для форм и панелей | Проверить выбранную архитектуру на реальной задаче | При неудаче CSP этап считается частично пройденным |
| Cytoscape в стабильном контейнере | Граф требует специализированной интерактивности | Граф не пересоздаётся при каждом SSE-патче |
| Rust4PM через адаптер | Повторно использовать парсер | Нет заявления о полном покрытии Apromore |
| Обычный DFG по соседним событиям | Семантика проста и проверяема вручную | Это карта процесса, не BPMN и не Split Miner |
| Память процесса и экспорт JSON | Уменьшить инфраструктурный объём | После перезапуска данные исчезают |
| Локальный доступ одного пользователя | Сосредоточиться на mining и интерфейсе | Не готово для многопользовательского размещения |

## Основные риски

1. Окружение: Rust/Cargo не обнаружены в PATH и стандартной пользовательской папке; Docker CLI есть, daemon недоступен. Первый этап должен обеспечить реальную сборку, а не полагаться на написанный код.
2. Legacy: восстановление Apromore может занять больше всего прототипа. На первичную диагностику выделяется ограниченное время. Если oracle не запущен, результаты маркируются как проверенные по контракту, без подтверждённой совместимости.
3. Импорт: порядок событий, пустые трассы, Unicode, lifecycle и timestamps меняют смысл графа. В ТЗ задана ограниченная семантика без скрытой сортировки и склейки событий.
4. Интерфейс: SSE может уничтожить состояние Cytoscape или применить устаревший ответ. Нужны версия анализа, стабильный контейнер и серверная проверка выбора.
5. Срок: установка компилятора и первая сборка съедают бюджет. Сначала рабочий путь, затем дополнительная интерактивность; последний час защищён для проверки и сдачи.
6. Лицензии: [ApromoreCore LICENSE](https://github.com/apromore/ApromoreCore/blob/development/LICENSE) — LGPL v3; [Rust4PM](https://github.com/aarkue/rust4pm) предлагает MIT/Apache-2.0. Лицензии каждого реально используемого компонента фиксируются отдельно; открытость проекта не отменяет этих условий.

## Почему план имеет смысл

Один вертикальный сценарий проверяет одновременно импорт, вычисления Rust, серверный интерфейс, SSE и границу JavaScript-компонента. Результат можно показать пользователю и проверить независимо на маленьком журнале. CRUD, пользователи и тяжёлая инфраструктура не дадут такой проверки mining-архитектуры за первые 8 часов.

Следующее решение принимается по результатам этого сценария: сохранять Datastar, менять только проблемный компонент интерфейса или пересматривать контракт. Количество написанных строк и субъективные оценки удобства не заменяют прохождение проверок.
