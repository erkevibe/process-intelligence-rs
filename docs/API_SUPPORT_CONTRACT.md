# Контракт HTTP API: основа 0.10, дополнения 0.11 и кандидата 0.12

Кандидат 0.12 добавляет необязательное `naive_timestamp_offset` в форму
`POST /csv/import`: фиксированное смещение `+HH:MM` или `-HH:MM`, не дальше
±14:00. Без него по-прежнему требуется пояс в отметке файла. Смещение уже
однозначной RFC3339-отметки не заменяется. Выбор отражается в предупреждениях
импортированного журнала; формат события и схема6 не меняются.

`POST /csv/performance` использует исходник из временного `/csv/preview`,
тот же token и выбранные case/activity/time/lifecycle/order, дополнительную
`start_timestamp_column`, `threshold_days` (1…3650, по умолчанию28),
`cohort=all|fast|boundary|slow`. Окончание берётся из `timestamp_column`.
`output=json` скачивает отчёт, иначе возвращается HTML. Обе колонки обязательны
для всех записей; неизвестное время не превращается в ноль. Сравнение границы
учитывает наносекунды, ровно на границе — отдельная группа. Суммы/минимум/максимум
в наносекундах передаются целыми строками. Источник и метод имеют SHA256,
авторская подпись не заявляется. Четыре группы содержат до50 подробных строк
каждого вида; общие счётчики и средняя длительность — по всей группе.

Просмотр доступен действующему editor/owner только для его token, пользователя
и проекта в пределах пяти минут с загрузки. Он не меняет базу и не потребляет
token; успешный импорт потребляет его. Неверные параметры/истёкший token дают422,
viewer —403, занятый общий CPU —422/busy, общие payload slots —503/cache_busy.
На форму установлен предел64КиБ, JSON-экспорт —8МиБ. Результат no-store.
Перекрытия и отрицательные интервалы сохраняются; ожидание ресурса не выводится.
Две отметки в постоянный формат события этим просмотром не добавляются.

Приёмка нового кандидата описывается в [Sprint35](SPRINT_35_REPORT.md).

Кандидат 0.11 добавляет `/quota` (GET: форма/состояние; POST: изменение только
владельцем) и `/quota/status` (GET: машинный учёт и версия проекта). POST
принимает `revision`, `mode=enabled|disabled`, `payload_allowance`; неизвестные
поля отвергаются. Устаревшая версия даёт 409, недостаточные права — 403.
Отказ квоты в общих platform-операциях отображается как 413 с кодом
`project_quota`; существующие импортные фасады могут вернуть 422 с тем же
кодом. Контракт не обещает единый HTTP-статус всех исторических фасадов.
Метрика, исключения и восстановление: [PROJECT_QUOTA_CONTRACT.md](PROJECT_QUOTA_CONTRACT.md).
Настройка `PI_PUBLIC_ORIGIN` разрешает один точный HTTPS origin для внешнего
прокси; без неё сохраняется локальный режим. Схема хранения кандидата — v6;
текущий статус приёмки — [SPRINT_30_REPORT.md](SPRINT_30_REPORT.md).

Ниже сохранён проверенный контракт основы 0.10. Его фиксированные наблюдения
Sprint29 относятся к тому исходному бинарнику; новый CI повторяет сценарий
на кандидате, не переписывая старые доказательства.

Это описание проверяемого поведения версии 0.10 и начало P3. Оно не вводит
SLA, сроки поддержки, удалённый доступ или допуск совместной эксплуатации.
Изменения поддерживаемого поведения должны сопровождаться обновлением этого
контракта и исполняемых проверок. Переход к Linux/TLS, OIDC, общей квоте,
нескольким экземплярам и HA остаётся отдельной очередью.

## Граница доступа

Сервер привязан к loopback. Проверка использует только явно названный
синтетический стенд `127.0.0.1:3147`; установленный пользовательский сервис
не затрагивается. У приложения сессионная аутентификация. Анонимный запрос
за защищённым ресурсом возвращает 303 на `/login`, поэтому клиент API должен
распознать перенаправление и не принять HTML входа за успешный JSON-результат.

Каждый ресурс читается в текущем проекте сессии. Знание идентификатора не
даёт доступа. Пользователь без членства не может открыть чужой проект;
запрос идентификатора из другого проекта возвращает 404. Viewer может читать
сохранённые задания и отчёты, но не запускать повтор, отменять или удалять
их. Снятие прав editor до viewer сохраняет чтение: это не удаление членства.
Права проверяются при каждом действии и перед публикацией результата.

## Сохраняемое построение

| Запрос | Назначение |
| --- | --- |
| `GET /logs/{log_id}/discovery/new` | HTML-форма с точной версией журнала и новым request_key |
| `POST /logs/{log_id}/discovery/jobs` | Принять построение: analysis_version, model_name, request_key |
| `GET /discovery/jobs/{job_id}` | Текущее сохранённое состояние и метаданные |
| `GET /discovery/jobs/{job_id}/events` | SSE с обновлением HTML состояния |
| `GET /discovery/jobs/{job_id}/view` | Страница задания и сохранённого результата |
| `GET /discovery/jobs/{job_id}/report` | JSON результата вместе с обучающим входом |
| `GET /discovery/jobs/{job_id}/bpmn` | Экспорт построенной модели |
| `POST /discovery/jobs/{job_id}/retry` | Новый запуск по сохранённому снимку с новым request_key |
| `POST /discovery/jobs/{job_id}/cancel` | Запрос отмены |
| `POST /discovery/jobs/{job_id}/delete` | Удалить завершённое задание с сохранением временной квитанции |

Для JSON-ответа на форму передавайте `Accept: application/json` именно в этом
виде. Для обычной HTML-формы успешный приём даёт 303 на страницу задания;
для JSON — 202 с метаданными. 202 не означает, что создано новое задание:
повтор прежнего запроса возвращает тот же ID, в том числе уже завершённый.

Идентификаторы непрозрачны. `snapshot.result_id` у построения указывает на
артефакт; ID модели находится в `model_id`. Версии — точные целые значения:
копируйте их из ответа или формы, не вычисляйте самостоятельно и не округляйте.
Запрос использует `application/x-www-form-urlencoded`; входные варианты
журнала клиент не подменяет — сервер сам сохраняет снимок.

Одинаковый request_key и те же параметры распознаются как повтор. Изменённая
форма с тем же ключом даёт 409. Новая устаревшая форма отклоняется, а уже
учтённый запрос распознаётся, пока сохранено задание или его квитанция.
Удалённое задание не создаётся заново по прежнему ключу. Ключи связаны с
пользователем и проектом; не переносите их между сессиями разных пользователей.

## Состояния и ошибки

Состояния: `queued`, `running`, `completed`, `failed`, `cancelled`. После
восстановления незавершённое задание имеет state `failed` и stage
`interrupted`; отдельного state `interrupted` нет. Названия вычислительных
стадий не являются журналом всех шагов: обновления могут объединяться.
Источником истины остаётся сохранённый snapshot, а не оптимистичная подпись UI.

| Наблюдаемый ответ | Значение |
| --- | --- |
| 202 / 303 | Запрос учтён либо распознан как повтор |
| 403 | Недостаточно прав |
| 404 | Ресурс отсутствует в доступном проекте |
| 409 | Конфликт сохранённых параметров, ревизии или состояния |
| 422 | Неподдерживаемые параметры или неверная форма |
| 429 | Исчерпана квота приёма или сохранённых заданий |
| 503 | Хранилище или данные временно недоступны |

Это не исчерпывающий список ответов транспорта. Ошибки домена при точном
`Accept: application/json` имеют code/message. HTML-запрос получает страницу
ошибки. Отказ разбора формы, неизвестное поле или превышение ограничения тела
может иметь ответ самого HTTP-фреймворка. Клиент сначала проверяет статус и
Content-Type, а затем разбирает тело; считать каждый отказ JSON нельзя.
Тело формы построения/повтора ограничено 4096 байт.

## Чтение, SSE и экспорт

Ответы обработчиков метаданных, результатов и SSE заданий имеют `Cache-Control:
no-store`. Эта формулировка не распространяется на перехват запроса до обработчика (например, redirect входа). Терминальный SSE закрывается и содержит состояние, а не полные
обучающие варианты и численные артефакты. Это HTML-события Datastar, не JSON
и не гарантированная очередь всех изменений. После потери связи прочитайте
snapshot заново; не запускайте POST автоматически из-за сетевой ошибки.

Оценка качества экспортируется с schema_version 1, method_sha256, evaluation
и input. Численная проверка выполняется `--verify-quality-report` с той же
методикой. Отпечаток метода, версия приложения и версия схемы PostgreSQL —
разные понятия. Старое приложение 0.9 отказывает схеме v5; это не разрешение
вручную менять журнал миграций. Порядок обновления описан в DATABASE_RECOVERY.md.

Другой журнал сам по себе не доказывает независимость обучения. Точная
training identity сохраняется отдельно; после обычного BPMN-импорта её нет.
Хеш результата проверяет целостность и связь со входом, но не подтверждает
автора. Экспорты и резервные копии реальных проектов содержат данные проекта;
синтетические файлы проверки не являются разрешением публиковать рабочие данные.

## Исполняемая проверка

`tools/sprint29/api-contract-probe.py` проверяет фиксированный собственный стенд:
owner/viewer/чужой проект, 303 входа, ошибки JSON/HTML, no-store, конечный SSE,
повтор одного запроса и сохранность проекта. Резервная копия принимается
только при HTTP 200, правильной схеме, digest и ожидаемых ресурсах, затем
сравниваются полные байты до и после чтений, повторов и отказов.

Probe сам подтверждает лишь совпадение отчёта с сохранённым seed-ответом.
Новый процесс и изоляцию базы доказывает внешний стенд с закреплёнными
программами, аргументами и полными завершёнными выводами. CI runner отдельно
останавливает seed-процесс, запускает другой PID и только затем выполняет probe.
Это не нагрузочный тест, аварийная остановка посреди вычисления, TLS-проверка
или гарантия производственной доступности. Полный P3 ещё не закрыт.

Проверки и ограничения первого инкремента — [SPRINT_29_REPORT.md](SPRINT_29_REPORT.md).
