# Техническое задание первого приближения

Версия 0.1 от 10 октября 2026 года. Статус: для защиты до разработки. Проект `process-intelligence-rs` должен дать локальному пользователю проверяемый анализ журнала XES за первый восьмичасовой цикл.

## Пользовательский сценарий

Пользователь открывает приложение, загружает XES, получает число cases, событий и activities, список вариантов трасс и DFG. Он выбирает узел или ребро, меняет минимальную частоту ребра и видит обновлённый граф без полной перезагрузки. Результаты можно выгрузить в JSON.

DFG означает directly follows graph: ребро A→B показывает, сколько раз событие B непосредственно следует за A внутри одной трассы. Это не модель BPMN, не вывод причинности и не обнаружение параллелизма.

## Архитектура

Один процесс Rust обслуживает HTTP через Axum, хранит локальные журналы в памяти, выполняет mining вне асинхронного HTTP executor и формирует HTML. Datastar обновляет панели через SSE. Cytoscape получает версионированный JSON графа через небольшой адаптер. Сервер владеет исходными данными и параметрами анализа.

Предлагаемые внутренние модули: `domain`, `event_io`, `mining`, `jobs`, `web`. Они могут находиться в одном crate; разделение на workspace crates допускается при реальной необходимости. Rust4PM скрыт за интерфейсом парсера. Версии Rust и зависимостей фиксируются; Cargo.lock публикуется.

В R1 данные не сохраняются между перезапусками. Это явно указано в интерфейсе. PostgreSQL, Arrow/Parquet и объектное хранилище вводятся после подтверждения базового сценария.

## Контракт журнала

| Объект | Поля и смысл |
|---|---|
| EventLog | log_id, имя, cases, warnings, время импорта |
| Case | Внутренний уникальный ID, необязательное имя `concept:name`, упорядоченные события |
| Event | ordinal, activity из event `concept:name`, необязательные timestamp и lifecycle |
| Analysis | log_id, analysis_version, counts, variants, полный DFG, параметры отображения |
| GraphView | analysis_version, min_edge_frequency, nodes, edges, selection |
| Job при T08 | id, state, stage, progress, result_id, error, cancel_requested |

Cases не сливаются при совпадении имени. Внутренние IDs стабильны в пределах загруженного журнала и не зависят от текста activity. Пользовательские строки не используются как HTML IDs или файловые пути.

## Импорт XES

- Поддерживается обычный UTF-8 XML XES с log/trace/event и атрибутами string/date, необходимыми для контракта. Поддержку namespaces проверяют fixtures. XES.gz, OCEL и CSV относятся к следующим этапам.
- В R1 порядок событий равен порядку XML внутри trace. По timestamp события не сортируются. Timestamp с явным offset при наличии нормализуется в UTC; дата без timezone отклоняется как неоднозначная.
- Отсутствующий timestamp допускается; если значение передано, но некорректно, журнал отклоняется с указанием case/event. Timestamp не участвует в DFG этого этапа.
- Каждое event обязано иметь непустой `concept:name`. Unicode сохраняется; trim используется только для проверки пустоты, исходное непустое имя не переписывается. Повторные ключи обязательного атрибута отклоняются.
- Отсутствующее имя trace допустимо. Пустые traces сохраняются: входят в число cases, дают пустой variant и не дают start/end или рёбер.
- Lifecycle сохраняется как атрибут. R1 считает каждое event самостоятельным событием; start/complete не склеиваются. В UI отмечается, что lifecycle normalization ещё не выполняется.
- Неиспользуемые атрибуты не влияют на расчёты; поддержка полного XES round trip не заявляется. Вложенные list/container и значения через global defaults не входят в контракт R1; при наличии, способном изменить обязательные поля, требуется явная ошибка неподдерживаемого формата.
- DTD/DOCTYPE отклоняются, внешние сущности не разрешаются. Загрузка ограничена до начала полного разбора. Повреждённый журнал не заменяет последний валидный анализ.

Предлагаемые пределы R1: 20 MiB на файл, 100 000 events, 20 000 cases и 4 KiB UTF-8 на activity. Пределы проверяются сервером; при превышении возвращается понятная ошибка. Это admission limits, а не обещание производительности.

## Статистика и DFG

Пусть trace имеет события a1…an. Activity count увеличивается на каждое событие. Для i от 1 до n−1 edge(ai, ai+1) увеличивается на 1. Граница cases никогда не создаёт ребро. Для непустой trace start(a1) и end(an) увеличиваются на 1. Self-loops сохраняются.

Вариант — точная последовательность activity, включая пустую. Частота варианта равна числу cases с этой последовательностью. Сортировка вариантов: частота по убыванию, затем лексикографическая последовательность; сравнение последовательностей не использует неоднозначную склейку строк.

Минимальная частота ребра — целое k≥1; отображаются рёбра с count≥k. Узлы всех наблюдавшихся activities остаются видимыми, включая изолированные. Фильтр изменяет представление графа; исходный журнал, статистика, variants и полные counts не меняются. Максимальное k — max(1, максимальная частота ребра + 1). Базовое значение k=1.

Порог не трактуется как аналог percentage filtering или preserve connectivity из Apromore. Retain/remove, частотная фильтрация traces и performance durations требуют отдельных контрактов.

## Ручной эталон

Вход: четыре cases со следующими activity sequences.

| Case | Последовательность |
|---|---|
| 1 | A, B, C |
| 2 | A, B, C |
| 3 | A, C |
| 4 | A, A |

Ожидание: cases=4, events=10, activities=3; counts A=5, B=2, C=3. Edges: A→B=2, B→C=2, A→C=1, A→A=1. Starts: A=4. Ends: C=3, A=1. Variants: ABC=2, AC=1, AA=1; строковые обозначения здесь только для чтения, в JSON передаются массивы.

При k=2 остаются A→B и B→C. При k=3 рёбер нет, узлы A/B/C остаются. Пустая trace добавляет один case и один пустой variant; не меняет events и edges.

Инварианты: сумма variant counts равна cases; сумма activity counts равна events; сумма edge counts равна сумме max(trace_length−1,0); суммы start и end равны числу непустых cases.

Metamorphic checks: дублирование всех traces удваивает counts; взаимно однозначное переименование activities сохраняет структуру; перестановка целых traces сохраняет DFG; сдвиг валидных timestamps не меняет граф.

## HTTP и SSE

| Метод и путь | Назначение |
|---|---|
| GET / | Экран загрузки и последний анализ |
| GET /health | Готовность процесса |
| POST /logs | Multipart загрузка, validation и создание анализа |
| GET /logs/{id} | HTML состояния анализа |
| GET /logs/{id}/export | JSON полного анализа и параметров текущего представления |
| POST /logs/{id}/view | Изменить k и получить обновление панелей через SSE |
| POST /logs/{id}/selection | Выбрать node/edge; сервер проверяет допустимость |
| GET /jobs/{id}/events при T08 | Progress и финальное состояние через SSE |
| POST /jobs/{id}/cancel при T08 | Запрос отмены |

Валидация: 400 для неправильных параметров, 404 для неизвестного ID, 413 для превышения byte limit, 422 для malformed/unsupported XES и semantic limits. Ошибка имеет стабильный код и понятный текст; детали exception не показываются пользователю.

После валидного импорта создаётся analysis_version. Ответы включают версию; устаревший ответ не перезаписывает новый граф. Изменения параметров одного анализа сериализуются на сервере. Выбор скрытого ребра сбрасывается после фильтра; pan/zoom сохраняются, пока остаётся тот же log.

Контейнер Cytoscape стабилен и исключён из morph обычных HTML-панелей. Связь с сервером ограничена четырьмя именованными действиями: threshold changed, node selected, edge selected, case selected при T08. Бизнес-логика фильтрации не дублируется в JavaScript.

В R1 допускается короткий SSE response на действие. Для долгой задачи при T08 — один канал на job, heartbeat, повторное получение snapshot после reconnect. WebSocket, брокер и обязательный HTTP/2 не нужны для локального spike. В отчёте отмечается, проверялись ли потери соединения.

## Фоновые задачи при T08

Состояния: queued → running → completed | failed | cancelled. Терминальные состояния неизменяемы. Очередь ограничена, одновременно выполняется один mining job. CPU work не блокирует обслуживание HTTP.

Progress отражает реальные этапы upload/parse/analyze/render; проценты по events показываются только там, где есть измеримый знаменатель. Искусственный таймер успеха запрещён. Cancel cooperative, проверяется на границах этапов и внутри собственного обхода данных. Если сторонний парсер не прерывается, UI честно показывает ожидание конца parse; результаты после принятой отмены не публикуются как completed.

При достаточной длительности контролируемого тестового job cancel приводит к cancelled и HTTP остаётся отзывчивым. Тестовый job не используется как демонстрация производительности настоящего discovery.

## Интерфейс и безопасность локального прототипа

Интерфейс на русском: upload, состояние анализа, cards статистики, таблица variants, граф, порог, selection details, export. Таблицы длинных журналов показывают ограниченный набор строк; полный результат остаётся в серверном анализе. Подписаны порядок XML, lifecycle policy и отсутствие сохранения после перезапуска.

По умолчанию server слушает 127.0.0.1. Без auth доступ извне не входит в эксплуатацию R1. Статические JS/CSS поставляются локально с зафиксированными версиями; runtime-зависимости от CDN нет. Activity names выводятся через escaping и JSON serialization, без вставки в исполняемые Datastar expressions.

CSP проверяется как HTTP header: script-src self и новый криптографический nonce на полную HTML-страницу; unsafe-eval отсутствует. Connect разрешён только к своему origin. Точная policy учитывает потребности canvas и стилей Cytoscape и фиксируется в коде. CSP-режим сверяется с [официальной документацией Datastar](https://data-star.dev/reference/security).

## Производительность

Контрольный benchmark: 10 000 events, 1 000 cases, 20 activities; отдельно фиксируются версия CPU/OS, профиль release/debug, wall time parse+analysis и peak RSS, если измерим. Предварительная цель — parse+analysis до 5 секунд в release и RSS до 512 MiB на доступной машине. Это проверяемая цель, не подтверждённая характеристика.

Большой тест с допустимыми лимитами должен либо завершиться, либо вернуть контролируемую ошибку без падения процесса. Результат benchmark не сравнивается с Apromore до измерения на одинаковых входах и оборудовании.

## Критерии приёмки

| ID | Обязательность | Критерий и способ проверки |
|---|---|---|
| AC01 | Базовый | Сборка и запуск по опубликованной инструкции из чистого checkout |
| AC02 | Базовый | Ручной fixture даёт все значения эталона; assertions независимы от реализации |
| AC03 | Базовый | Invalid XML, empty activity, duplicate key, unsupported format и limits отклоняются |
| AC04 | Базовый | Пустые traces, singleton, self-loop и Unicode имеют заданную семантику |
| AC05 | Базовый | Инварианты и четыре metamorphic checks проходят |
| AC06 | Базовый | Upload → stats → variants → graph → threshold → export выполнен в браузере |
| AC07 | Базовый | SSE обновляет граф без полного reload; stale responses не меняют новое состояние |
| AC08 | Базовый | Pan/zoom и допустимый selection сохраняются; скрытый selection сбрасывается |
| AC09 | Базовый | CSP работает без unsafe-eval; HTML в activity отображается как текст |
| AC10 | Базовый | JSON содержит schema_version, counts, parameters и version; соответствует серверу |
| AC11 | Базовый | Лимиты и benchmark измерены либо помечены failed/unverified, без выдуманных чисел |
| AC12 | Базовый | fmt, clippy и meaningful tests проходят на опубликованном commit; отчёт доступен |
| AC13 | Дополнительный | Реальный job progress, cancel и отсутствие completed после принятой отмены |
| AC14 | Дополнительный | Case selection согласован с details и graph после изменения view |
| AC15 | Следующий этап | Сопоставление с зафиксированной версией Apromore на одинаковой нормализации |

Все базовые AC нужны для статуса «первое приближение готово». Непройденные AC явно перечисляются; частично работающий экран не считается полным выполнением ТЗ. AC15 не входит в обещание R1 и не заменяется сравнением новой реализации с самой собой.

## Поставка

Исходники, lockfile, README запуска, синтетические fixtures с ожидаемыми данными, автоматические проверки, screenshots рабочего сценария, JSON example, manifest зависимостей и evidence report. Отчёт привязан к commit SHA и содержит статусы passed/failed/unverified, фактическое время, benchmark и статус oracle.

В публичный репозиторий не попадают секреты, исходная частная переписка, реальные пользовательские event logs и скачанные datasets без проверки права распространения. Для тестов R1 создаются собственные синтетические журналы.
