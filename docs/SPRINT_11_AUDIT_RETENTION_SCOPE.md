# Sprint11: граница 512/513 в аудите владельца

Конечная проверка исходного R3-02 на новой копии штатной резервной базы 0.7.2. Полная матрица производителей аудита остаётся открытой.

Количество переименований выводится из фактического начального total выбранного проекта: сначала до 512, затем ещё одно до 513. Все события создаются реальным owner API; SQL не используется для наполнения аудита. Ожидаемый полный Auth-документ выводится из PRE: меняются только название/revision выбранного проекта, Auth revision и его audit trail. Каждое событие проверяется по actor/project/resource/action/revision/policy SHA/outcome; время ограничено интервалом соответствующего HTTP-запроса. Остальные пользователи, сессии, права, области аудита и все non-Auth строки сохраняются.

На 512 сохраняются 512 событий без потерь. На 513 остаются последние 512 в прежнем порядке, total=513 и dropped=1. Полный API-экспорт сопоставляется с ожидаемой проекцией; неизвестные верхние поля и секретные Auth-поля не допускаются.

Viewer не может переименовать проект, owner получает отказ по устаревшей revision. Полное состояние после отказов совпадает с PRE; viewer не видит owner Auth-audit, foreign получает проекцию собственного проекта. После штатной остановки PostgreSQL и повторного запуска приложения проверяются полный снимок и побайтный экспорт. Отдельная verification copy не запускается в приложении и не используется для входа; её состояние и каталог сохраняются.

Проверка относится к одному producer project_renamed и одной Auth-owner области. Успех не закрывает весь business audit, все операции жизненного цикла/CAS, browser/Datastar или весь R3. Прежние базы, архивы и неудачные прогоны не изменяются. Начало допускается до 16:45 UTC, завершение ограничено 17:00 UTC; общий runtime freeze — 17:21 UTC.
