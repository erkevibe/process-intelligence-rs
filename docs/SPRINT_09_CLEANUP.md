# Offline retained legacy cleanup: candidate operator contract

Developer draft, not independent acceptance. R3-04 stays OPEN until the complete unchanged Sprint09 corpus and actual F01/F02/F03 pass on the frozen candidate. No automatic startup, HTTP, scheduled cleanup or automatic retry exists.

Stop source and verification applications yourself. Keep an existing complete stock database backup and its original manifest inside the installation `.local` directory. `tools/cleanup-legacy.ps1 -Mode Preview -BackupFile <archive> -PlanFile <new-private-plan> -Database <source> -TargetDatabase <new-pi_restore_name>` explicitly invokes the maintained stock restore into a NEW database, leaves failed targets for inspection, then validates the actual live database identities and full managed state. The source is never restored over. The wrapper uses the existing private operator configuration; credentials appear only in child environment, never arguments, plans or output. PowerShell prerequisites remain those of the maintained stock backup/restore helper.

Preview emits the SHA256 of a new private plan, candidate row count and logical JSONB-text bytes. The plan binds exact executable bytes/build version, archive and original manifest hashes/size, actual `(system_identifier, database_oid)` pairs, schema checksum, complete digest inventory and sequence state, and exact candidate keys/versions/Rust-serde source hashes. Payloads and secrets are absent. The archive manifest alone is insufficient: a new restore must equal complete source managed state. Same actual identity, unsupported schema/objects, inaccessible identity privileges, any other client backend, stale values or marker failures refuse the entire batch.

Apply uses the same source/restore/archive/plan and `-ConfirmPlanSha256 <exact-sha>`. It takes both existing application advisory leases in deterministic actual-identity order; final locks cover all five managed tables before the first snapshot. Source locks are SHARE ROW EXCLUSIVE and restore locks SHARE. Parameterized DELETE removes only the exact verified legacy keys at their exact versions and verifies the complete RETURNING set. Every remaining managed value/version/marker/ledger timestamp and resource-sequence definition/last value/is_called must match the expected complete post-state before the one commit. Verification restore remains unchanged. No hidden audit or migration-marker mutation is introduced.

Source and restore complete snapshots run concurrently only after both lock sets are acquired, with a separate exclusively borrowed transaction/client per worker. Both workers are joined before propagating errors, DELETE or COMMIT. Pre-state schema checks and all-row hashes remain complete; post-state hashes of both databases are recomputed in full. A worker error/panic refuses before commit and leaves transaction rollback to the normal scoped/drop paths. This removes serial waiting between independent database reads; it does not raise any timeout or establish that the full historical final transaction fits ten seconds. That feasibility must be measured independently on the exact optimized candidate.

SQL statements retain 5-second, locks 2-second and transactions 10-second budgets; connection timeout is 5 seconds. The separate pre-apply validation phase has a 300-second cooperative deadline checked between complete row/log checks and before entering the final transaction; this does not increase SQL/lock/transaction budgets. Initial stock restore remains a separate maintained helper operation. At most 10,000 total managed rows, each identifier/key at most 512 UTF-8 bytes, and private plan/receipt at most 4 MiB. Heavy read-only validation works one retained repository and one normalized log/model at a time outside the final transaction. Existing Platform startup ownership invariant is reused: normalized headers belong to known Auth projects, while untouched Auth projects may lack a lazily created header. Full state JSONB SHA256 digests are computed on pinned PostgreSQL18.6; these are a separate domain from migration eligibility SHA256 of exact Rust `serde_json::to_vec<Value>` bytes. A streaming writer must equal the existing Rust serializer in focused tests. Unversioned administrator/sequence writes outside offline ownership are not prevented by these table locks.

After the complete row-count and key-length checks, each transaction sets four local planner options: `max_parallel_workers_per_gather=4`, `min_parallel_table_scan_size=0`, `parallel_setup_cost=0`, and `parallel_tuple_cost=0`. One materialized UNION ALL query computes every fingerprint from all five tables, with the same tagged arrays, complete JSONB-text SHA256 domain and deterministic key order; ledger order remains numeric. The resource sequence is read separately in full. PostgreSQL may execute the independent table scans concurrently. Worker availability is not guaranteed, and a timeout still refuses safely. These settings do not change server configuration or any timeout. The measured read-only experiment does not establish final Apply acceptance; the complete final PRE/DELETE/POST transaction requires independent verification on the new candidate.

On known successful commit, receipt creation is separately reported. `cleanup_committed_receipt_failed` means the database commit succeeded but private receipt persistence failed; never infer rollback or reapply automatically. A commit transport failure returns `cleanup_outcome_unconfirmed` and read-only complete reconciliation: `complete_pre`, `complete_post`, `unexpected_state_stop` or `unavailable_stop`. It does not retry or call a platform/startup migration. Save the original output and plan, then resolve the recorded state. Empty valid source/restore/plan returns `cleanup_empty` with zero database writes; an old nonempty plan cannot be reused after cleanup.

Logical removed bytes are not physical PostgreSQL file shrink. No VACUUM FULL or directory deletion is performed. Recovery restores the original archive into another NEW database, independently validates full PRE state, and then uses the current compatible application's documented restore/start path. Never reinsert legacy JSON into an active normalized database or silently switch the application's database.

Native interface: `cleanup::run("verify"|"apply")` and flags `--cleanup-storage-verify`/`--cleanup-storage-apply`. Private environment: `PI_DATABASE_URL`, `PI_CLEANUP_RESTORE_URL`, `PI_CLEANUP_ARCHIVE`, `PI_CLEANUP_PLAN`, `PI_CLEANUP_CONFIRM_SHA` for Apply, optional `PI_CLEANUP_RECEIPT` (default plan path + `.receipt.json`). Native artifact paths must be absolute, canonically inside `.local` beneath the current installation working directory, without symlink/junction traversal. The wrapper selects the installation working directory temporarily and restores the prior directory. Caller must provide private restricted parent directories; wrapper establishes and verifies the current-user access-section ACL before credentials/artifacts. Parent global environment is restored in `finally`. CLI exit0 is reserved for verified/committed/empty results; unconfirmed outcome exits3 and known commit with failed receipt exits4, after printing the structured result.
