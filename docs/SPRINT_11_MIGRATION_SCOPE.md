# Sprint11: конкретные отказы схемы и откат

Новый изолированный stock-пакет 0.7.2, полный manifest и штатный setup/import. От его новой резервной копии создаются четыре отдельные базы: будущая версия ledger, неверная контрольная сумма v2, готовая схема для повторного offline запуска и схема v2 для отказа старого бинарника 0.3.0. Прежние установки и сохранённые стенды не используются для запуска.

Ожидаемые сообщения фиксируются до исполнения:

| Случай | Ожидается |
|---|---|
| Будущая версия, обычный/offline запуск | Код 1: «Схема базы не поддерживается или повреждена. База не изменена; используйте совместимую версию и резервную копию.» |
| Неверная контрольная сумма v2, обычный/offline запуск | Код 1: «Схема или сохранённые данные не поддерживаются. Исходные записи не изменены; проверьте состояние миграции.» |
| Готовая схема, offline повтор | Код 0, полное состояние без изменений |
| Старый 0.3.0 на схеме v2 | Код 1 и конкретный отказ неподдерживаемой схемы |

Для каждого случая сохраняются полные managed-строки, sequence и определение sequence, исходный ledger, структурный каталог/ACL и сведения о триггерах до и после. Подтверждение требует полного совпадения, конечного native-кода и завершённых потоков. Общая ошибка доступа или занятый порт не заменяют отказ схемы.

Отдельная небольшая причинная база v1 содержит исходный baseline ledger и одну неизменяемую запись. Event trigger вызывает ошибку при первом CREATE TABLE внутри транзакции v2. Требуются настоящий текст этой ошибки в журнале собственного PostgreSQL, полный откат состояния/каталога, удаление только установленного тестового триггера, успешный повтор и сохранение исходной записи, ledger v1 и sequence. Ещё один повтор должен стать no-op.

После этих проверок отдельный этап запускает приложение на новой восстановленной готовой копии. Полные снимки сохраняются перед login, после login и после выбора проекта. Ожидаемое Auth-состояние выводится из PRE: прежние пользователи, права, аудит и непросроченные сессии сохраняются; добавляется одна сессия с восьмичасовым сроком из фактического интервала запроса; выбор проекта меняет только её project_id. Каждая операция увеличивает Auth revision на один. Все остальные managed-строки и каталог должны совпасть. Cookie и пароли остаются в закрытых файлах.

Небольшая причинная база не заменяет полный исторический перенос, миграцию реальных проектов/Auth или проверку прав после миграции. Конечный Auth delta не закрывает весь session/lifecycle/CAS договор. Браузер/Datastar и приёмка всего R3 остаются отдельной работой. Частичные и неудачные прогоны сохраняются без автоматического повтора.
