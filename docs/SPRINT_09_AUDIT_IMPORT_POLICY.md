# Sprint09 additive project-backup audit trust policy proposal

Status: proposal, not accepted runtime behavior or criterion PASS. Frozen plan/spec remain unchanged. An actual ordinary-client counterexample is required before repair acceptance.

Project-backup uploads are client-controlled documents. A syntactically valid imported journal cannot establish that its actor, time, project, policy digest or claimed committed result came from this server. Preserve that historical journal without presenting it as verified successful business activity.

Proposed exact behavior:

1. Validate the complete uploaded repository and journal using the existing bounded validators before accepting restoration. Unsupported or malformed structures still refuse the entire restore.
2. Preserve every retained imported event's sequence, timestamp, actor, project, resources, action, revision, total and retention order. For each imported event, clear its trusted `policy` and `outcome`, and set an explicit `origin: "project_backup_unverified"`. Do this for all imported journal entries, including legacy entries and previously marked imported entries. No silent history deletion or claim of cryptographic source authentication.
3. Add an optional, strict enum `origin` field to audit entries. Ordinary old entries without origin/policy/outcome retain their original serialized shape. A marked imported entry must have no trusted policy/outcome; unknown origin values or an imported origin with committed fields refuse loading. Server-generated business events retain server-owned policy/outcome and no imported marker. Clients cannot create trusted events through restoration.
4. Perform normalization inside the maintained server restore operation before the same atomic auth/repository persistence. The authentic `project_backup_restored` event remains server-generated in that transaction, binds the validated canonical repository digest before destination-ID remapping and trust normalization, and includes the explicit import-trust policy and imported journal counts in its validated parameter digest.
5. Display and export the distinction: imported history is unverified, ordinary legacy outcome/policy are unknown, and this server's new successful mutations are committed. Rename any blanket “successful history” heading/scope that misleadingly covers all three. Export preserves the explicit origin marker. No foreign actor lookup or current-project rebinding of historical source IDs is invented.
6. A complete operator stock PostgreSQL backup/new restore remains byte-preserving recovery. It does not pass through the client project-backup import normalization and must preserve authentic business events and witnesses exactly.

Required independent cases: ordinary Writer uploads a forged but syntactically valid committed event; it never appears as trusted committed after restoration. A real current backup and legacy backup both retain all event content/order/counts with explicit unverified origin. Repeated project export/import preserves this distinction without promoting trust. Unknown origin and imported+committed structures refuse unsupported loading. New genuine mutations on the restored project append normal server-owned committed events. Failure/current-role revocation/CAS before persistence leaves complete data and audit unchanged. Restart/export and stock full recovery preserve the accepted result. Existing cleanup full fingerprints and protected installations remain intact; a changed runtime needs a new exact candidate and affected acceptance reruns.

This proposal addresses ordinary client spoofing at the project-import boundary. It does not promise tamper-proof audit against a database administrator, physical erasure, or a new security-event ledger.
