# Преобразование журналов и сетей Петри

`pi_convert` — утилита для файлов. В Sprint20 её вариант для 0.7.5 независимо проверен на 57 сценариях, 16 отдельных обратных вызовах и девяти дополнительных границах; тот спринт не менял сервер и интерфейс. Эти исторические доказательства сохранены. Утилита принимает свои входные файлы, а не только примеры из репозитория.

С версии 0.8.0 тот же код используется страницей «Преобразования» и фоновыми заданиями. В кандидате 0.8.1 место в общей очереди резервируется до чтения загрузки или сохранённого исходника для повтора. Приёмка интеграции и резервирования описывается отдельно от прежних проверок CLI: [основной отчёт](SPRINT_21_REPORT.md), [продолжение спринта](SPRINT_21_CAPACITY_REPORT.md). Для сервера требуются PostgreSQL и схема V3; порядок обновления, отмены и восстановления приведён в [инструкции эксплуатации](CONVERSION_OPERATIONS.md).

Поддерживаются четыре направления в пределах [точного контракта](R5_CONVERSION_CONTRACT_DRAFT.md):

| Команда | Результат |
|---|---|
| `xes csv` | Плоский XES → таблица событий CSV |
| `csv xes` | Таблица событий CSV → плоский XES |
| `petri-json pnml` | JSON `PetriNet` из `process_mining 0.6.2` → согласованный PNML |
| `pnml petri-json` | Согласованный PNML → JSON `PetriNet` |

Для сборки из корня исходников с установленным закреплённым Rust toolchain:

```text
cargo build --locked --example pi_convert
```

При стандартном каталоге Cargo исполняемый файл находится в `target/debug/examples/pi_convert.exe` на Windows и `target/debug/examples/pi_convert` на Linux. Если задан `CARGO_TARGET_DIR`, путь начинается с этого каталога.

Формат вызова:

```text
pi_convert FROM TO INPUT NEW_OUTPUT_DIRECTORY [--allow-metadata-loss]
```

Например, в PowerShell из корня репозитория:

```powershell
.\target\debug\examples\pi_convert.exe xes csv '.\data\orders.xes' '.\orders-csv'
.\target\debug\examples\pi_convert.exe csv xes '.\data\events.csv' '.\events-xes'
.\target\debug\examples\pi_convert.exe petri-json pnml '.\data\net.json' '.\net-pnml'
.\target\debug\examples\pi_convert.exe pnml petri-json '.\data\net.pnml' '.\net-json'
```

На Linux начало команды заменяется на `./target/debug/examples/pi_convert`; остальные аргументы те же. Родительский каталог результата должен существовать, а сам `NEW_OUTPUT_DIRECTORY` — отсутствовать. Для каждого вызова выбирайте новый каталог. Вход — обычный файл UTF-8 до 20 MiB; символические ссылки и reparse points не допускаются.

При успехе каталог содержит `report.json` и один `payload.csv`, `payload.xes`, `payload.pnml` или `payload.json`. В отчёте указаны направление и профиль, SHA256 и размеры входа/результата, статус, потери и нормализации, предупреждения парсера, а для сетей — проверенное соответствие узлов. `converted` означает завершение одного направления. Существующие файлы не перезаписываются. При штатном отказе создаётся только отчёт, код завершения — 2. Ошибка чтения, записи или аргументов может завершить вызов без отчёта.

Публикуются полностью записанные файлы; при обычной ошибке записи предусмотрена очистка созданных файлов. Это не гарантия одновременной аварийно-атомарной публикации двух файлов при отключении питания. После прерванного вызова проверяйте наличие обоих файлов и соответствие SHA256 из отчёта; не принимайте оставшийся каталог за успешное преобразование.

## Журналы: что сохраняется и что отклоняется

CSV имеет ровно четыре основные колонки в указанном порядке:

```csv
case,activity,timestamp,lifecycle
```

Разделитель — запятая; кавычки, запятые и переносы внутри полей экранируются по RFC4180. Вне кавычек строки заканчиваются CRLF; одиночный LF отклоняется. Пустая ячейка времени или lifecycle означает отсутствие значения. Строки одного case должны идти подряд: повторное появление case после другого case отклоняется. Header-only CSV представляет пустой журнал.

XES должен быть плоским. У каждой непустой трассы есть уникальный непустой `concept:name`; события имеют непустое имя активности. Пустые трассы и отсутствующие либо повторяющиеся имена трасс отклоняются, чтобы не объединять разные случаи и не терять события. Максимум — 20 000 трасс и 100 000 событий, имя активности — до 4096 байт UTF-8.

Сохраняются порядок трасс, порядок событий и основные поля событий. Сортировка по времени и объединение lifecycle-пар не выполняются. Внутренние сгенерированные ID и ordinal разных парсеров могут различаться: они не выдаются за сохранённые идентификаторы источника. Их происхождение и нормализации отражаются в отчёте.

Время — RFC3339 с часовым поясом, не более девяти цифр дробной секунды. Результат записывается в UTC `Z` без потери наносекунд. Наивное время, leap second и лишняя точность отклоняются. Ненулевое исходное смещение теряется как отдельное представление часового пояса и требует явного разрешения; сам момент времени сохраняется.

По умолчанию утилита отказывает при потере дополнительных атрибутов, имени журнала, classifiers/extensions, дополнительных CSV-колонок или ненулевого смещения. Чтобы разрешить только предусмотренные контрактом потери метаданных:

```powershell
.\target\debug\examples\pi_convert.exe xes csv '.\data\rich-flat.xes' '.\rich-core-csv' --allow-metadata-loss
```

Сначала изучите `report.json`: он перечисляет фактические потери и их расположение. Флаг не разрешает объединять трассы, удалять события, принимать global/list/container или восстанавливать потерянные поля при обратном вызове. Неизвестные структуры, некорректные значения, дубликаты ключей и неправильные типы основных полей остаются отказами. Встроенные XML-экранирования и числовые ссылки на допустимые символы поддерживаются; DTD, внешние и объявленные пользователем сущности запрещены. Схемы и сетевые ресурсы не загружаются.

## Сети Петри: точная структура вместо сходства по числу узлов

`petri-json` — собственная serde-схема `PetriNet` библиотеки `process_mining 0.6.2`, а не произвольный JSON графа. Допускаются обычные взвешенные дуги между местами и переходами, повторяющиеся подписи переходов, tau, начальная и несколько конечных разметок. Проверяются полные веса и явные записи разметок, включая нули. Пропущенная разметка и пустые коллекции не считаются автоматически одинаковыми.

Пределы: 1–128 мест, до 128 переходов и 256 узлов суммарно, до 1024 дуг и 32 конечных разметок. Веса — положительные `u32`, токены — `u64`; ограничение оценщика в 255 токенов здесь не применяется. Дубликаты ID/JSON-ключей/дуг, неверные ссылки и доли вместо целых чисел отклоняются.

PNML ограничен одним net и одним page согласованного обычного диалекта. Внешние расширения, графика, цветные/ингибиторные/reset/read дуги и неизвестные элементы не поддерживаются. Пустые или обрезаемые импортёром подписи, CR/LF в подписях и непредставимые маркировки отклоняются. Tau обозначается только согласованным маркером; видимая подпись `Tau` не становится невидимым переходом.

Настоящий upstream-импортёр генерирует новые UUID. Утилита должна проверить и записать полную биекцию мест и переходов с сохранением подписей, tau, всех взвешенных дуг и каждой разметки. Сходства названий или количества узлов недостаточно. При исчерпании поиска результат — `inconclusive`, без успешного payload. Перенумерация UUID и форматирование XML — объявленные нормализации, не обещание побайтного совпадения. Оценки fitness, корректность исполнения и soundness преобразование не доказывает. Флаг потери метаданных не расширяет допустимую семантику PNML.

## Как выполнить настоящее обратное преобразование

Для сетей `evidence.normalization_inventory` содержит фактические нормализации: поле, сторону преобразования, точное место, исходное и полученное значение. Счётчики вычисляются по этим записям. Полная карта ID включает неизменившиеся идентификаторы; отсутствующие имена мест или tau-маркеры не создают записей.

Обратный вызов запускается отдельно и читает именно полученный payload:

```powershell
.\target\debug\examples\pi_convert.exe xes csv '.\data\orders.xes' '.\forward'
.\target\debug\examples\pi_convert.exe csv xes '.\forward\payload.csv' '.\reverse'
```

Для сети аналогично:

```powershell
.\target\debug\examples\pi_convert.exe petri-json pnml '.\data\net.json' '.\net-forward'
.\target\debug\examples\pi_convert.exe pnml petri-json '.\net-forward\payload.pnml' '.\net-reverse'
```

Проверьте оба отчёта. Равенство исходных байтов не предполагается: сравниваются согласованные основные поля журнала либо полный граф и разметки сети с соответствием ID. Обратное преобразование после разрешённой потери сравнивается только с явно указанной основной проекцией; оно не возвращает удалённые метаданные. Наличие отчёта первого вызова само по себе не доказывает, что обратный вызов выполнен.
