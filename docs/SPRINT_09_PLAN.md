## Постоянное удаление: принятая политика после голосования

1. Только owner целевого проекта через действующую session с актуальными правами; target заранее архивирован. Архивирование остаётся обратимым. Для работы owner имеет другой доступный активный проект; чужой проект не выбирается как замена.
2. Отдельная страница предпросмотра показывает имя и точный ID, версию, количество журналов/моделей/папок/участников и незавершённых jobs. Подтверждение требует точного ID и отдельной явной фразы удаления, привязано к версии и digest предпросмотра; повтор/stale/чужие поля отказывают. При nonterminal jobs отказ; обход этого условия отсутствует.
3. Одна PostgreSQL-транзакция сравнивает актуальный auth CAS и repository CAS, сохраняет безопасное свидетельство результата и удаляет точно auth project/membership/session references, project records/header, migration marker и retained legacy key этого ID. Все остальные проекты, пользователи, данные и sequence сохраняются. Никаких независимых последовательных commit для разных доменов.
4. Сессии участников целевого проекта переводятся только в их собственный доступный активный проект; при отсутствии такого проекта завершаются. После успеха runtime cache/pending previews этого проекта очищаются; старые captured actors/workers не могут снова опубликовать результат. Lock order repository→Auth→DB сохраняется; Auth callback не захватывает repository.
5. Минимальное свидетельство удаления сохраняется отдельно от удалённых repository/auth project: бывшим owners видны actor ID/project ID/action/policy/time/committed result и counts без имён файлов, содержимого, паролей и сессий. Отдельная ограниченная история512 на каждого бывшего owner, с total/dropped и экспортом; чужая активность не вытесняет его записи. UUID удалённого проекта не используется повторно.
6. Интерфейс прямо говорит: постоянное удаление необратимо без заранее сохранённой копии; копии и PostgreSQL MVCC могут продолжать хранить данные. Автоматическая полная backup/newrestore на каждом UI-delete не вводится: текущая auth/session может измениться после backup, а stock full restore является offline operator operation. Удаление не утверждает наличие проверенной копии пользователя. QA обязана фактически проверить full backup/new restore и отдельное восстановление до удаления на собственном наборе. Это явное решение по предпочтению Customer, а не фиктивная галочка «backup verified».

## Аудит успешных бизнес-действий

Конечный объём — существующие поддержанные mutation routes: создание/переименование/архив/восстановление/удаление проектов, предоставление доступа и создание пользователей; импорт XES/CSV и подтверждение preview, job transitions/recovery, изменение фильтров/календаря/представления, создание/изменение моделей, folder create/rename/move/delete/assignment, project backup restore. Для каждой группы фиксируются версия конкретной политики, проверенные параметры либо digest полной сохранённой политики, actor/project/resource IDs, UTC-время, revision и `committed` outcome. Поля старых событий отсутствуют и помечаются «политика/результат не сохранены»; не дописываем успех задним числом.

Audit+mutation атомарны. Refusal/intent не представляются как успешная запись; полный отдельный security log всех отказов не входит в этот business-success ledger. Существующие512 последних project/auth событий и новый owner deletion ledger имеют явные монотонные счётчики/retention/export. Policy не принимает произвольные пользовательские поля; secrets и payloads не копируются. RBAC актуален при чтении и записи; старый actor/session не разрешает подмену или чтение чужого. Изменение persisted JSON имеет явную backward-read/unsupported-downgrade политику; существующий schema2 DDL не меняется молча.

## Очистка retained legacy: отдельная CLI операция

Контракт `docs/SPRINT_08_CLEANUP_PROPOSAL.md` принимается заново в рамках этой итерации с текущими владельцами/сроком; его прежние исторические STOP и временные ворота не являются текущими состояниями. Технические safety conditions и corpus `docs/SPRINT_09_CLEANUP_CORPUS.md` сохраняются: полныеC01–C18 со всеми независимыми subcases, реальныеF01/F02/F03, полный неизменённый historical old0.3 archive, full backup/new verification restore, полная equality PRE/POST всех managed values/versions/markers/ledger/sequence.

Только Preview→private plan→Apply exactSHA, действительные `(system_identifier,database_oid)` вместо сравнения URL, два offline leases, dedicated side-effect-free clients без startup DDL/Platform/login. Полные locked rechecks до DELETE, точные ключи+версии, одна commit, restore остаётся неизменным. Legacy source hash — точные Rust serde bytes; полное managed-state сравнение — отдельный PostgreSQL JSONB hash domain. Не повышаем5sSQL/2slock/10stransaction budgets, не сокращаем fixture/rows ради успеха. Не обещаем немедленное уменьшение физических файлов. Cleanup не добавляет скрытую DB audit mutation; приватные plan/receipt — отдельные артефакты операции.

Наблюдатель фактического PostgreSQL протокола проходит независимый TD review до fault runs: F01 beforeDELETE, F02 успешный DELETE→перехват следующего COMMIT до передачи, F03 подтверждённый успешный серверный COMMIT→потеря ответа клиенту. Production sleeps/fault flags/bypass запрещены. Uncertain ACK возвращает явный неподтверждённый исход и выполняет только read-only complete PRE/POST reconciliation, без blind retry. Receipt-write failure после known commit отличается от rollback. Восстановление — только в ещё одну новую базу, не поверх source.
