# Sprint32: офлайн-миграция с файловым секретом

Статус: кандидат P3 после принятого [PR44](https://github.com/erkevibe/process-intelligence-rs/pull/44), main `426a2e7bfefd427a3a2ced69b3946a536ddf4137`. Реализация подготовлена; успешное выполнение нового сценария пока не заявлено. [Предыдущая приёмка служб](SPRINT_31_REPORT.md), [обслуживание установки](LINUX_SERVICE_OPERATIONS.md).

Цель — соединить ранее раздельные проверки: офлайн-команда `--migrate-storage`, файловый секрет и systemd. На новой GitHub-hosted Ubuntu24.04 сначала без изменения выполняется богатый сценарий Sprint31 из скачанной поставки: отчёт, квота, права, восстановление, смена пароля и сертификата. Его журнал остаётся отдельным, а прежний строгий контракт19 сценариев/136 команд не расширяется и не ослабляется.

После штатной остановки приложения и Caddy две собственные временные службы запускают тот же бинарник с `--migrate-storage`. Секрет передаёт LoadCredential; в конфигурации окружения находится только путь, URL и ephemeral-режим явно исключены. Службы имеют Type=oneshot, RemainAfterExit=yes, Restart=no, отдельные User/Group, NoNewPrivileges и ProtectSystem=strict. Короткий процесс не наблюдается через `/proc`: фиксируются настройки unit и фактические результаты завершения, а не выдуманные UID/NoNewPrivs CLI.

Семь критериев нового сценария:

1. Фиксированные имена и пути временных units отсутствуют до изменений.
2. Повтор миграции уже корректной v6 завершается exit0 и не меняет полный снимок базы.
3. Только в собственной синтетической восстановленной базе намеренно заменяется checksum строки версии6. CLI должен завершиться настоящим exit1/Result=exit-code, оставив повреждённый снимок неизменным. SuccessExitStatus не маскирует отказ.
4. Явное восстановление исходного checksum этой fixture возвращает точный снимок до проверки. Это не инструкция исправлять рабочую базу вручную.
5. Новый процесс приложения после обычного запуска сохраняет отчёт, квоту, учёт и доступ наблюдателя.
6. В журналах временных units нет известных синтетических секретов, сессий и приватного ключа.
7. Обе обычные службы и временные команды остановлены до удаления собственной цепочки firewall.

Наблюдения и приватные захваты Sprint32 отделены от Sprint31. Firewall остаётся включённым во время всей дополнительной фазы; при неподтверждённой остановке он сохраняется. При ошибке fixture отбрасывается вместе с VM, автоматического исправления повреждённой базы нет. Публикуются только выбранные JSON: без дампов, ключей, raw-журналов и секретов.

Новый сценарий проверяет повтор v6 и отказ на неверном checksum через файловое подключение. Он не заменяет отдельную проверку обновления v5→v6, восстановления кластерных ролей, перезагрузки машины или допуска production-сервера. Пользовательский сервис3131 и локальные PostgreSQL/app не используются.

Выбор режима временной службы основан на [systemd-run](https://www.freedesktop.org/software/systemd/man/255/systemd-run.html): RemainAfterExit удерживает unit для чтения результата. Здесь не используются wait/pipe; collect также выключен, чтобы не потерять unit до чтения отказа. Пределы исходного стенда не увеличены, TimeoutStartSec CLI20s и TimeoutStopSec10s.
