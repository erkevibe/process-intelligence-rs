# Sprint32: офлайн-миграция с файловым секретом

Статус: инкремент P3 в [PR45](https://github.com/erkevibe/process-intelligence-rs/pull/45) после принятого [PR44](https://github.com/erkevibe/process-intelligence-rs/pull/44), main `426a2e7bfefd427a3a2ced69b3946a536ddf4137`. Исходник `d7726620a062e1be72ea849d8107d9d40cb65128` прошёл все восемь заданий двух CI: [40141713441](https://github.com/erkevibe/process-intelligence-rs/actions/runs/40141713441), [40141711345](https://github.com/erkevibe/process-intelligence-rs/actions/runs/40141711345). Новый сценарий выполнил7 проверок,50 команд и10 зарегистрированных HTTP-запросов; прежний строгий профиль19/136 также прошёл. Итоговые проверки конкретного head находятся в Checks PR. [Предыдущая приёмка служб](SPRINT_31_REPORT.md), [обслуживание установки](LINUX_SERVICE_OPERATIONS.md).

В первых запусках CLI завершился exit0, но сам стенд отказал на сравнении LoadCredential как строки. Ограниченная диагностика7121952 подтвердила, что systemctl255 выводит это свойство как `[unprintable]`. Исправленный стенд запрашивает типизированное значение через D-Bus: GetUnit связывает объект с точным именем службы, LoadCredential имеет тип `a(ss)` и ровно пару имени и исходного пути. Содержимое секрета не запрашивается. Формат подтверждён [исходником systemd v255](https://github.com/systemd/systemd/blob/v255/src/core/dbus-execute.c) и [busctl JSON](https://www.freedesktop.org/software/systemd/man/255/busctl.html), а затем реальным прогоном. Прежние отказы сохранены и не выданы за успех.

Цель — соединить ранее раздельные проверки: офлайн-команда `--migrate-storage`, файловый секрет и systemd. На новой GitHub-hosted Ubuntu24.04 сначала без изменения выполняется богатый сценарий Sprint31 из скачанной поставки: отчёт, квота, права, восстановление, смена пароля и сертификата. Его журнал остаётся отдельным, а прежний строгий контракт19 сценариев/136 команд не расширяется и не ослабляется.

После штатной остановки приложения и Caddy две собственные временные службы запускают тот же бинарник с `--migrate-storage`. Секрет передаёт LoadCredential; в конфигурации окружения находится только путь, URL и ephemeral-режим явно исключены. Службы имеют Type=oneshot, RemainAfterExit=yes, Restart=no, отдельные User/Group, NoNewPrivileges и ProtectSystem=strict. Короткий процесс не наблюдается через `/proc`: фиксируются настройки unit и фактические результаты завершения, а не выдуманные UID/NoNewPrivs CLI.

Семь критериев нового сценария:

1. Фиксированные имена и пути временных units отсутствуют до изменений.
2. Повтор миграции уже корректной v6 завершается exit0 и не меняет полный снимок базы.
3. Только в собственной синтетической восстановленной базе намеренно заменяется checksum строки версии6. CLI должен завершиться настоящим exit1/Result=exit-code, оставив повреждённый снимок неизменным. SuccessExitStatus не маскирует отказ. Нормализованная причина `schema_unsupported` устанавливается стендом только после наблюдения известного сообщения CLI с совпадающими PID и unit; это не отдельный машинный код, напечатанный бинарником. Исходный журнал остаётся приватным.
4. Явное восстановление исходного checksum этой fixture возвращает точный снимок до проверки. Это не инструкция исправлять рабочую базу вручную.
5. Новый процесс приложения после обычного запуска сохраняет отчёт, квоту, учёт и доступ наблюдателя.
6. В журналах временных units нет известных синтетических секретов, сессий и приватного ключа.
7. Обе обычные службы и временные команды остановлены до удаления собственной цепочки firewall.

Наблюдения и приватные захваты Sprint32 отделены от Sprint31. Firewall остаётся включённым во время всей дополнительной фазы; при неподтверждённой остановке он сохраняется. При неожиданном сбое сценария fixture отбрасывается вместе с VM: в finally нет автоматического исправления базы. Плановое восстановление checksum происходит только после подтверждения ожидаемого отказа. Публикуются выбранные JSON без дампов, ключей, raw-журналов и секретов.

Выбранный архив скачан отдельно и проверен по GitHub ZIP SHA256 `3fb3013ebc015c47d81e5cf4f99ed5e5468dd63b4c25125ca96f68890beba303`. Данные находятся в `evidence/sprint32/offline-migration` и относятся к указанному d772662, а не к будущим коммитам. Проверка без PostgreSQL и root:

```text
python3 -I -B tools/sprint32/verify-offline-evidence.py evidence/sprint32/offline-migration --self-test
```

Контролёр сохраняет строгую проверку базового Sprint31, затем сверяет7 новых результатов, порядок50 команд/8 устойчивых HTTP-наблюдений, реальные коды завершения, типизированную привязку секрета, источник сообщения по PID/unit, пять отпечатков снимков и неизменные идентификаторы отчёта/проекта. Заданы14 отрицательных проверок семантических подмен. Он проверяет целостность и согласованность наблюдений, а не повторяет root-операции и не удостоверяет авторство. CI запускает его для сохранённого примера, внутри скачанного пакета и для свежего протокола; результаты этих новых интеграций требуют CI соответствующего head.

Новый сценарий проверяет повтор v6 и отказ на неверном checksum через файловое подключение. Он не заменяет отдельную проверку обновления v5→v6, восстановления кластерных ролей, перезагрузки машины или допуска production-сервера. Пользовательский сервис3131 и локальные PostgreSQL/app не используются.

Выбор режима временной службы основан на [systemd-run](https://www.freedesktop.org/software/systemd/man/255/systemd-run.html): RemainAfterExit удерживает unit для чтения результата. Здесь не используются wait/pipe; collect также выключен, чтобы не потерять unit до чтения отказа. Пределы исходного стенда не увеличены, TimeoutStartSec CLI20s и TimeoutStopSec10s.
