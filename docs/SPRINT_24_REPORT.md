# Sprint24: API и эксплуатационные проверки

Работа основана на `74d997f5429d2e49d4ca25362aef72e6ab746d12`.
Rust-код, Cargo и прежний бинарник 0.8.2 в этом спринте не изменены.
Дополнены проверяющие сценарии, операторская диагностика и инструкции.
Завершённые CI и проверка скачанного точного коммита учитываются отдельно
в PR этой поставки; сохранённый опыт сам по себе не подтверждает доставку.

## Текущий API

На отдельной синтетической базе выполнены 238 HTTP-запросов и 219 проверок:
11 профилей фильтров, пять календарных профилей, отрицательные формы,
согласование HTML/JSON, последовательные проверки прав и явный повторный
запуск приложения. Проверялись полные данные случаев и порядковые номера
событий, исходный журнал, сохранённые параметры, экспорт и аудит.
Календарные ожидания включают весенний и осенний переходы Berlin — два и
четыре часа соответственно, праздничный день и отсутствующие отметки.

Проверка относится к названному конечному HTTP-контексту. Все возможные
маршруты и сочетания ролей не заявляются: положительный календарь редактора
и анонимный календарный запрос отдельно не выполнялись. Нет нового
браузерного/Datastar-прогона, повторного Java-вычисления или заявления о
совместимости со всем Apromore.

Сохранены 13 записей нативных процессов и 26 полных потоков вывода.
Долговечные журналы запросов и проверок сверены с каждым сырым HTTP-ответом.
Вызов fsync завершился; отдельный контроль имитирует оборванный хвост, но
это не опыт с физическим отключением питания.

## Отказ базы и восстановление

Отдельный прогон содержит 25 HTTP-запросов / 25 проверок, 25 процессов /
50 полных потоков. Второй экземпляр на ту же базу отказал, первый сохранил
готовность и данные. При штатной остановке PostgreSQL тот же экземпляр
приложения отвечал 503 `storage_unavailable`; изменения фильтра и календаря
не подтверждались. Возврат PostgreSQL не снял состояние отказа прежнего
адаптера. Только явный перезапуск приложения вернул 200.

Резервная копия, экспорт и проектная часть аудита сохранились. Три полных
SQL-снимка бизнес-данных совпали побайтно. Обе генерации PostgreSQL
завершились штатно; контроль вывода, ресурсов и границ остановки принят
независимо. Это конечный локальный контракт, без HA, автоматического
переподключения или обещанного времени восстановления.
[Последовательность для оператора](DATABASE_RECOVERY.md).

## Диагностика объёма

Реализован [отчёт только на чтение](CAPACITY_DIAGNOSTIC.md) для PostgreSQL
18: количество проектов и шести видов записей, физические размеры пяти
управляемых таблиц и базы. Отчёт не устанавливает квоту и не читает
document/auth/session. Логические количества видны в транзакции; физические
байты наблюдаются во время выполнения, а их пересекающиеся области нельзя
складывать. WAL, другие базы, резервные копии и свободное место исключены.
Исправленный сценарий принят независимо: 19 процессов / 38 полных потоков.
Отчёт размером 1346 байт завершился одним JSON, маркером после COMMIT и
кодом 0. Ручное ожидание — один проект, по одной записи log_state, log_data,
log_source и log_analysis, без model и conversion — подтвердилось.

Реальная попытка INSERT в той же READ ONLY-транзакции отказала с SQLSTATE
25006; контрольная строка осталась единственной со значением 17. Пустая
схема и неизвестный вид записи дали отдельные отказы 22023. После
подтверждённого удержания блокировки другим сеансом отчёт отказал по
тайм-ауту 55P03 до освобождения блокировки. Все четыре отказа вернули код
3 и не напечатали маркер успешного завершения. PostgreSQL остановлен чисто.
Это отдельные проверки на малой базе, без обещания масштабируемости,
квоты или полной сертификации схемы.

## Сохранённые неудачи

API01 остановился при достижении лимита INFO-вывода: из 20 потоков 19 полны,
один обрезан. Старый несохранённый журнал запросов из памяти не восстановлен.
Для следующей попытки перспективно принят больший лимит двух потоков
приложения и долговечный журнал наблюдателя.

API02 сохранил 190 запросов и 202 успешные проверки до ошибки проверяющего:
POST Form с неверным числом возвращает 422, а не ожидавшийся GET-статус 400.
Исправлено ожидание по закреплённой реализации Axum; продукт не менялся.

Ops01 остановлен 25-секундной защитой обхода файлов **до** остановки базы.
14 процессов / 28 потоков сохранены. Завершённые копии публичного Git были
архивированы с независимой сверкой всех 13 236 файлов до удаления ровно
двух выбранных деревьев. Прежние исходные архивы и дополнительные результаты
сохранены. Один последующий обход занял 13,424 секунды; он не доказывает
единственную причину тайм-аута и не гарантирует будущую задержку. Лимит
25 секунд и метрика нативного выделенного места не ослаблены.

Capacity01 остановился на ошибке типа в проверяющем: корректное JSON-число
1 PowerShell прочитал как Int64, а проверка разрешала только Int32.
SQL завершился успешно с маркером COMMIT; отрицательные сценарии ещё не
были выполнены. Сохранены 11 процессов / 22 полных потока, отдельно записан
контроль типа. Перед новым запуском выполнено обычное восстановление WAL
с чистой остановкой PostgreSQL. Исправлена только проверка целого типа
Int32/Int64; bool и дробные числа не принимаются. Прежний отказ сохранён.

Шесть исторических UNKNOWN и первая невосстановленная причина прежнего
аварийного захвата остаются открытыми; новый успех их не исправляет.

## Проверка публичных свидетельств

Публичный набор содержит явно выбранные сохранённые ответы, журналы,
описания процессов и решения независимых проверяющих. Пароли, cookies,
закрытые состояния и значения конфигурации исключены. Локальные пути
заменены только в публичном представлении: манифест хранит отдельные
размеры и SHA256 оригинала и копии. Хеши исходных нативных потоков в
описаниях процессов сохраняют прежнее значение. Числовые лексемы,
включая FILETIME, не пересериализуются.

```text
python -I -B tools/sprint24/check-saved.py evidence/sprint24/saved
```

Повтор проверяет согласованность сохранённых файлов, журналов и описаний.
Он не является новым выполнением исходных HTTP-утверждений или опытом
восстановления. [Назначение сценариев](../tools/sprint24/README.md).

## Дальше к enterprise

1. Завершить точную поставку этого кандидата: независимая приёмка,
   стандартный CI, проверка фактически скачанных файлов и завершения процессов.
2. Согласовать метрику общей квоты и пределы; затем спроектировать атомарный
   учёт всех путей записи, удаления и восстановления, резерв для отмены и
   терминальных ошибок, правила старого бинарника. Произвольная квота здесь
   не вводится.
3. Расширить автоматизацию резервного восстановления и переносимой поставки.
4. Отдельно спроектировать несколько экземпляров и HA. Текущая защита
   единственного писателя и ручной перезапуск этого не обеспечивают.

Enterprise-готовность, общий SLO и весь возможный API этим спринтом не
объявляются. Исторические конечные R5-профили и новые расширения разделены
в [карте R5](R5_ACCEPTANCE_MAP.md).
