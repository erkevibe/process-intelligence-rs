# Linux с TLS: профиль и приёмка установки

Статус: шаблоны проверены в одноразовом Linux CI с настоящим TLS и явным
временным CA; контрольные наблюдения — [SPRINT_30_REPORT.md](SPRINT_30_REPORT.md).
В Sprint31 скачанная поставка уже прошла отдельный запуск как служб systemd
на одноразовой Ubuntu24.04; [точный статус и границы](SPRINT_31_REPORT.md).
Проверка целевого сервера, публичного DNS и сертификата организации ещё не выполнена.
Это не приёмка production, HA или обещание SLA.
Порядок остановки, копирования, восстановления и смены секретов —
[обслуживание служб](LINUX_SERVICE_OPERATIONS.md).

Один Linux-хост: Caddy принимает HTTPS, приложение слушает только127.0.0.1,
PostgreSQL доступен приложению локально. Сеть между приложением и PostgreSQL
в этом профиле не защищена TLS: библиотека использует NoTls. Удалённый
PostgreSQL за пределами локального защищённого транспорта этим профилем
не покрывается. Не публикуйте порты приложения или PostgreSQL наружу.

## Файлы и секреты

Поставка приложения размещается в /opt/process-intelligence/current целиком,
включая static и fixtures, с владельцем root и правом чтения служебной учётной
записи process-intelligence. Файл database-url в /etc/process-intelligence
создаёт оператор: root:root0600, одна строка PostgreSQL URL. Не помещать
его в репозиторий, командную строку, журнал или публичное доказательство.
PI_DATABASE_URL_FILE читает до16KiB; одновременные URL и FILE отвергаются.

В /etc/process-intelligence/app-environment указать PI_PUBLIC_ORIGIN по
app-environment.example: ровно внешний HTTPS origin, совпадающий с Caddy.
Пути, query, userinfo, wildcard и пустые значения не допускаются. DNS-имя
задаётся в ASCII (для IDN —punycode A-label), стандартный443 нормализуется.
IPv4 задаётся четырьмя десятичными частями без сокращений, octal/hex aliases
не поддерживаются. IPv6 нормализуется; IPv4-mapped IPv6 (`::ffff:...`)
отвергается из-за различий записи в браузере и стандартной библиотеке.
Этот параметр разрешает точные Host/Origin для форм; он сам не включает TLS.
Локальные HTTP адреса backend сохраняются для служебных проверок; публичный
localhost/127.0.0.1 origin с тем же портом отвергается как неоднозначный.
Подставленные forwarded headers не расширяют разрешённые адреса.

deploy/linux/process-intelligence.service использует systemd LoadCredential
(нужна поддерживающая эту директиву версия systemd). Секрет читается из
каталога credentials, а в окружении находится только путь. Бинарник запускается
от отдельной учётной записи с запретом записи в системные каталоги.
Миграция не входит в ExecStart: перед обновлением остановить службу, сделать
проверяемую копию и явно выполнить --migrate-storage совместимым бинарником
с тем же credential. Возврат к старому бинарнику требует согласованной копии
старой схемы; удаление строки версии не является откатом.

## TLS

В /etc/caddy/Caddyfile установить deploy/linux/Caddyfile. В отдельном
/etc/process-intelligence/caddy-environment указать реальные host/cert/key
по образцу caddy-environment.example. Полную цепочку и приватный ключ выдаёт
оператор действующей системы сертификатов; ключ читает только Caddy и root.
Это профиль с явно предоставленным сертификатом: автоматическое получение
или продление через ACME здесь не настроено. Автоматическое управление
сертификатами выключено; HTTPS и явный HTTP redirect настроены отдельно.
Продление и перезапуск Caddy
должны быть частью проверенного процесса оператора.

Drop-in caddy-process-intelligence.conf рассчитан на /usr/bin/caddy.
Перед установкой сверить путь с фактическим пакетом и его службой; не
перезаписывать другие сайты существующего Caddy. Административный listener
выключен. Изменение сертификата/конфигурации применяется контролируемым
перезапуском, который может оборвать SSE; долговечность результатов
обеспечивает база, повторное открытие страницы восстанавливает состояние.

HTTP перенаправляется на HTTPS с сохранением пути и параметров. Caddy
добавляет Secure к session cookie, включая её удаление; приложение сохраняет
HttpOnly и SameSite=Strict. Подставленные заголовки имени пользователя
не предоставляют доступ. HSTS задан на сутки без includeSubDomains/preload.
Для SSE используется стандартная немедленная передача text/event-stream.

Версия стенда Caddy2.11.7 и SHA256 Linux-amd64 архива закреплены в
tools/sprint30/run-linux-tls-ci.sh. Выбор соответствует опубликованному
релизу; обновление версии требует повторной проверки. Источники:
[Caddy release](https://github.com/caddyserver/caddy/releases/tag/v2.11.7),
[TLS](https://caddyserver.com/docs/caddyfile/directives/tls),
[reverse proxy и SSE](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy),
[systemd credentials](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html#Credentials).

## Приёмка отдельной установки

До допуска реальных пользователей проверить реальный hostname и доверенную
цепочку, отказ для неверного имени/CA, HTTP redirect, вход/выход/Secure cookie,
права Viewer/Editor/Owner, большие допустимые загрузки, SSE, сохранённые
отчёты, перезапуск службы и согласованное восстановление копии. Отдельно
проверить firewall, отсутствие внешнего доступа к3000/PostgreSQL, свободное
место, журналы, обновление сертификата и восстановление после обновления.

CI использует только временный собственный CA с SAN localhost, порты
8080/8443/3147 и выделенную синтетическую базу. CA передаётся клиенту явно,
глобальное доверие не меняется; режимы отключения проверки TLS запрещены.
Этот протокольный стенд дополнен отдельным заданием systemd из скачанного
артефакта: LoadCredential, реальные uid/NoNewPrivs, перезапуск и остановка
служб с сохранением отчёта и квоты. Расширение Sprint31 на стандартных80/443
проверяет также восстановление базы, смену пароля роли и ручную замену
сертификата; окончательный статус указан в отчёте Sprint31. Перезагрузка
всей VM и целевой сервер в эту проверку не входят.

Архив содержит `PACKAGE_MANIFEST.json` с точным коммитом и контрольными суммами,
а также `BUILD_ENVIRONMENT.json` с Linux/архитектурой/glibc/Rust среды сборки.
Проверка архива в отдельном Linux-задании не обещает совместимость со всеми
дистрибутивами или более старой glibc. Сверьте эти сведения с целевым сервером
до установки и выполните сценарий приёмки именно на нём.
