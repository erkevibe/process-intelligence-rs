## Календарь

Настоящий `CalendarModelBuilder` создаёт отдельную модель для каждого входа.
Основное измерение — `CalendarModel.getDuration(Instant, Instant).toMillis()`.
Второй метод `getDurationMillis` измерен отдельно: его результат не подменяет
основной. Rust вызывает существующий `calendar::business_millis`.

| Пример | Apromore, мс | Rust, мс или отказ |
|---|---:|---:|
| Обычный рабочий день | 32400000 | 32400000 |
| Обрезанный интервал | 2700000 | 2700000 |
| Выходные | 7200000 | 7200000 |
| Праздник | 0 | 0 |
| Kathmandu, смещение +05:45 | 32400000 | 32400000 |
| Berlin, весенний переход | 10800000 | 7200000 |
| Berlin, осенний переход | 10800000 | 14400000 |
| Рабочая граница в весеннем gap | 5400000 | `calendar_boundary` |
| Рабочая граница в осеннем fold | 5400000 | `calendar_boundary` |
| Неизвестная зона | `ZoneRulesException` | `calendar_timezone` |
| Конец рабочего дня раньше начала | -57600000 | `calendar_policy` |
| Обратный интервал | 0 | `calendar_policy` |
| Длительность 1,250 секунды | 1250 | 1250 |

Все 13 исходных гипотез подтвердились. Шесть основных длительностей совпали;
семь остальных строк сохраняют объявленные различия семантики или отказов.
Для последней строки второй Java API вернул **1251**, основной — **1250**.
Это различие API, а не потеря точности при сравнении.

Фактически наблюдались Java tzdb **2026b** и Rust IANA **2025b**
(`chrono-tz 0.10.4`). Java смещения конечных точек независимо сопоставлены
с закреплёнными UTC-моментами. Rust напрямую не выдаёт смещения в этом
наблюдателе: проверена его фактическая длительность против заранее выведенных
UTC-сегментов, без заявления о прямом наблюдении всех Rust offsets.
Публичные конфигурации и исходные входы сохранены до и после обоих Java API.
Сохранность скрытых внутренних кэшей не заявляется.

## Фильтры

Настоящий `APMLogFilter.filterIndex` вызван один раз с упорядоченным списком
правил; результат прочитан через исходные immutable trace indexes и valid-event
BitSet. Сравниваются полные выбранные трассы и события, их исходные позиции,
порядок, атрибуты и сохранность входа. Выбор не пересчитывается собственной
копией предиката. Rust вызывает существующий фильтр журнала.

Шесть полных совпадений: закрытый диапазон длины 2–3, только нижняя граница,
только верхняя граница, сохранение выбранных activity, удаление выбранных
activity и последовательность «длина, затем сохранение activity».
В варианте с одной нижней границей Java явно передаётся точный
`Long.MAX_VALUE = 9223372036854775807`; JSON сохраняет все его цифры.

Два заранее обозначенных различия остаются различиями: Apromore возвращает
пустой результат при перевёрнутом диапазоне, Rust отказывает `filter_range`;
при удалении всех событий Apromore удаляет опустевшую трассу, Rust её сохраняет.
Все восемь исходных гипотез подтвердились. Прежнее конечное покрытие Sprint18
сохраняется отдельно; данный набор не заменяет его и не покрывает все фильтры.

## Проверка и публичные данные

Java-наблюдатели скомпилированы из зафиксированных исходников коммита
`75575480e645b663bfe58c8d9a82e4b681ca3da0`, без изменения upstream.
Компиляция отделена от вызовов API. До и после проверены 5763 исходных Git
blob, 285 runtime-файлов, точный упорядоченный classpath из 189 записей,
все 504 файла существующего JDK и три реально полученных класса наблюдателей.
[Метаданные реальной сборки](../evidence/sprint19/core-reference-environment.json)
публикуют хеши этих файлов, исходников и классов, а также явно производные
записи компиляции. Это привязка к ранее принятому JDK, без заявления о новой
проверке подлинности дистрибутива и без публикации upstream-бинарников.
JVM использует отдельные временные и домашние каталоги, 512 MiB heap,
ограниченные процессы и полные закрытые потоки. Календари и фильтры запускались
последовательно. Старые установки и пользовательские данные не изменялись.

Независимый QA проверил все 27 календарных и 17 фильтровых native-записей,
исходные потоки, типизированные входы, выборки, дроби времени, смещения и
сохранность данных. Отдельные десять контрпримеров проверяют сравниватели;
один тест проверяет сохранение числовых лексем при публикации. Эти тесты
не выдаются за результаты движков.

[Календарный набор](../evidence/sprint19/core-calendar/projection-manifest.json)
содержит 70 участников плюс манифест;
[фильтровый](../evidence/sprint19/core-filter-extended/projection-manifest.json)
— 45 участников плюс манифест. Полные синтетические JSON-наблюдения сохраняют
каждую исходную числовую лексему. Только явно объявленные локальные пути
заменены псевдонимами; исходные и опубликованные хеши указаны раздельно.
Записи процессов сохраняют исходные размеры и хеши приватных потоков;
сами консольные потоки не публикуются.

Повторить сравнение опубликованных полей можно без Java и Rust, используя
Node 24; оба выходных файла должны отсутствовать:

```text
node tools/oracle/compare-core-calendar.mjs evidence/sprint19/core-calendar/java-index.json evidence/sprint19/core-calendar/rust-index.json NEW-calendar.json
node tools/oracle/compare-core-filter-extended.mjs evidence/sprint19/core-filter-extended/java-index.json evidence/sprint19/core-filter-extended/rust-index.json NEW-filter.json
```

Конечные пары преобразований R5-03 и отдельные quality/timing/memory настоящего
SplitMiner R5-04 этим сравнением не закрываются. Измерения не меняют выбранную
продуктовую политику DST или обработки пустых трасс; изменение политики требует
отдельного согласованного поведения и проверки.
