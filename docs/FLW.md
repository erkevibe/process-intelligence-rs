# Frame Logical Work для разработки Process Intelligence Core

FLW применяется как цикл накопления проверенных исполняемых решений: Experience → Evidence → Hypothesis → Verification → Verified Executable Unit → Composition → Selection → Inheritance. Первые 8 часов используют минимальный проектный протокол; полноценный learning runtime относится к отдельному проекту.

Основа взята из соседнего чата «Сравнение ECC и FLW». Из него используется принцип Evidence ≠ Verification: наблюдение или уверенное описание не подтверждает воспроизводимый эффект. Исторические команды и заявленные результаты экспериментов из других чатов не являются текущими разрешениями и не используются как доказательство ускорения этой разработки.

## Три слоя

| Слой | Что хранится | Как используется |
|---|---|---|
| Memory | Наблюдения, ошибки окружения, контекст | Источник кандидатов; не исполняемая политика |
| Hypotheses | Условия, действие, ожидаемый результат | План эксперимента, ещё не проверенное решение |
| Verified units | Исполняемый payload, verifier и evidence | Локальное повторное использование в зафиксированной области |

## Карточка задачи

Для каждой T-задачи из плана создаётся запись с полями:

- id, purpose и scope;
- condition и failure_region;
- action/payload, dependencies и версия API;
- expected_effect и verifier;
- cost_budget и фактические затраты;
- risk, provenance и lineage;
- attempts с exit status и ссылками на evidence;
- status и причина изменения статуса.

Evidence содержит SHA кода и входного fixture, параметры, версию среды, ожидаемый и фактический результат, вывод проверки. Ссылки на отчёты не заменяют само выполнение. Имена локальных пользователей, секреты и приватные логи в публичном evidence не записываются.

## Жизненный цикл

candidate → testing → verified. Провал verifier оставляет запись rejected с причиной; повторная попытка имеет новую запись и lineage. Регрессия переводит verified → suspect. Успешная повторная проверка возвращает verified; подтверждённая несовместимость даёт deprecated.

Проверенный test-run доказывает только заявленную область входов и версий. Он не создаёт статистическую гарантию надёжности и не повышает доверие только из-за количества наблюдений.

## Пример проверяемой гипотезы

H-DFG: если XES сохраняет порядок событий внутри cases и каждая activity валидна, обход соседних событий даст частоты ручного эталона из ТЗ.

Payload — реализация DFG, verifier — ручной fixture и invariants/metamorphic checks. Failure region — unsupported XES, lifecycle pairing, timezone-dependent reordering и Apromore percentage filtering. Успешный verifier даёт локальную единицу DFG-counting для этой области, без утверждения полной совместимости Apromore.

## Композиция

U-import + U-dfg + U-render → C-analysis. Все три компонента могут пройти свои проверки, но композиция требует нового browser/API verifier: upload, корректные counts, изменение threshold, SSE, отсутствие stale updates и экспорт.

Если composition verifier проходит, C-analysis становится отдельной локальной проверенной единицей с собственной версией и lineage. Это позволяет повторно использовать доказанную связку и отличать ошибку парсера от ошибки адаптера интерфейса.

## Проверки внутри 8 часов

На старте T-задачи записывается hypothesis. После попытки сохраняется факт выполнения и ошибка. После verifier фиксируется статус. На T09 проверяется композиция. На T10 публикуется сводка фактических результатов; неподтверждённые кандидаты остаются неподтверждёнными.

Минимальное хранение: `flw/records/*.json`, `flw/evidence/` и краткий индекс. Эти записи создаются по мере реальной разработки; на стадии защиты нет выдуманных verified units. На следующем этапе формат можно перенести в PostgreSQL. Vector retrieval, hooks и MCP не обязательны для минимального протокола.

## Наследование и цель

Решения остаются somatic/project-local. Germline promotion требует transfer tests в другой задаче или среде и отсутствия регрессий; успех одного fixture не является основанием для глобального наследования.

Purpose фиксируется пользовательским сценарием и критериями ТЗ. При провале сборки меняется подход к окружению; при несовпадении counts — реализация или нормализация; при избыточной сложности интерфейса — конкретный UI component. Критерии не переписываются задним числом ради статуса «готово».

Минимальный FLW-протокол не выдаётся за завершённый FLW runtime: автоматическое gene discovery, mutation, recombination search, calibrated trust и межпроектная эволюция в R1 отсутствуют.
