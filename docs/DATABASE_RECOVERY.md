# PostgreSQL: обновление и восстановление

Для текущих обычных и компактных отчётов см. [порядок восстановления полной
базы](CURRENT_DATABASE_RESTORE.md) и [конечный опыт Sprint24](SPRINT_24_DR_REPORT.md).
Исторические миграции ниже сохраняют свои отдельные версии и ограничения.

## Текущая последовательность при недоступности базы

Для проверенного экземпляра 0.8.2 после потери PostgreSQL `/health`
отвечает 503 `storage_unavailable`. Даже после возвращения PostgreSQL
прежний экземпляр остаётся в этом состоянии. Восстановление соединения
без перезапуска не обещается.

1. Сохраните журналы и сведения о последней подтверждённой операции.
2. Восстановите доступность нужного PostgreSQL обычными средствами его
   поставки. Не удаляйте вручную PID-файл, WAL или исходную базу.
3. Явно остановите прежний экземпляр приложения и запустите его с той же
   проверенной конфигурацией. Второй экземпляр на ту же базу должен отказать.
4. Убедитесь, что `/health` вернул 200, затем проверьте данные, экспорт и
   аудит. Ответ 200 сам по себе не заменяет проверку содержимого.

Sprint24 проверяет эту последовательность на отдельной синтетической базе:
штатная остановка PostgreSQL, отказ операций при недоступности, возврат
базы и явный перезапуск приложения. Это конечная проверка, без обещания HA,
срока восстановления или результата незавершённой транзакции. Правила
резервного восстановления и исторические миграции ниже сохраняют свои
отдельные ограничения. [Диагностика объёма](CAPACITY_DIAGNOSTIC.md)
помогает собрать сведения о базе, но не заменяет резервную копию.

Версия0.4 использует schema v2 с отдельными записями журналов и моделей. Обычный запуск базы0.3 требует явной офлайн-миграции. Сначала проверенный backup и восстановление отдельной копии, затем tools/migrate-storage.ps1, после завершения Start.ps1 -Database pi_restore_<имя_копии>. Старые пользовательские базы в спринте04 не обновляются. [Контракт v2 и порядок миграции](STORAGE_V2.md). Проверенный backup/restore/migration путь0.4 использует проверенный PowerShell7.6.5; native Start отдельно проверен в Windows PowerShell5.1. Полная цепочка backup в5.1 на стенде не подтверждена. Описание v1 ниже относится к историческому пути0.2→0.3.

Версия приложения 0.3 использует PostgreSQL 18 и аддитивную schema v1. До чтения аккаунтов/проектов берётся singleton lease; при инициализации схемы тот же ключ защищает миграцию до любого DDL. После завершения schema transaction краткая initialization lease освобождается; Platform берёт длительную lease до чтения auth/cache. Другой Platform не может изменять схему под работающим экземпляром.

Существующие `public.pi_kv` и `public.pi_resource_sequence` распознаются по столбцам, primary key, свойствам sequence, ограничениям и отсутствию неизвестных table triggers/rules/indexes/RLS. Сохраняемые auth/repository документы должны читаться без утраты полей и иметь поддерживаемые ссылки/модели. Другие ключи generic Database сохраняются без преобразования и не считаются контрактом произвольной прикладной схемы. Миграция добавляет positive version constraint и `public.pi_schema_migrations` (version/name/checksum/applied_at) в одной транзакции. Future version, изменённый checksum и неизвестная структура запрещают запуск до записи. Новые миграции потребуют отдельного номера/checksum и проверок; изменение старого SQL не разрешается как upgrade.

## Перед обновлением

Остановите собственное приложение, сделайте полный database backup и проверьте восстановление в отдельную БД. Project JSON не содержит аккаунты/сессии и не заменяет backup PostgreSQL. Рабочая пользовательская установка 0.2 в спринте 03 не обновляется: все испытания выполняются на отдельных тестовых базах; версия 0.3 поставляется отдельно.

Пример из каталога установки (путь архива внутри приватной `.local`; файл должен быть новым):

```powershell
powershell -ExecutionPolicy Bypass -File tools/database-backup.ps1 -Mode Backup -BackupFile .local/backups/before-03.dump
powershell -ExecutionPolicy Bypass -File tools/database-backup.ps1 -Mode Restore -BackupFile .local/backups/before-03.dump -TargetDatabase pi_restore_before03
```

Помощник читает private config в памяти, проверяет SHA256 архива и восстанавливает одной транзакцией в **новую** `pi_restore_*` БД. Если target уже существует, он не изменяется. Если restore не удался, отдельный target остаётся для диагностики, исходная БД сохраняется. Используются `pg_dump`/`pg_restore` той же поставки PostgreSQL; глобальные роли/настройки кластера и файлы private config в database dump не входят. Роль `pi_app` создаётся bootstrap отдельно. Архив содержит password hashes и sessions: храните его приватно, не публикуйте. Не полагайтесь на backup до проверки exports, аккаунтов и прав в восстановленной БД.

Downgrade через запуск 0.2 на изменённой БД не поддерживается: старый бинарник не проверяет schema version. Для возврата используйте сохранённый прежний кластер/config или проверенный pre-upgrade backup в новую БД. Не удаляйте исходный кластер.

## Задачи после остановки

Число журналов не задаёт предел объёма проекта: один журнал содержит исходные данные, результат фильтрации и анализ. Перед записью проверяется консервативная оценка двоичного JSONB, включая контейнеры, ключи и числовые значения. Нижний бюджет новых данных и новых задач — 266 272 768 байт оценки; верхний для уже принятых задач и восстановления — 268 369 920 байт. Разница 2 MiB оставлена для сохранения отмены, ошибки и результата восстановления. Это оценка JSONB, а не размер загруженного XES или JSON-файла; допустимое число больших журналов может быть меньше восьми. Основание ограничения — [формат и проверка контейнеров PostgreSQL 18](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/utils/adt/jsonb_util.c).

Новые журналы, модели, фильтры и другие изменения содержимого используют нижний бюджет. Превышение возвращает `project_capacity` до очереди SQL, не отключает базу и не заменяет прежний проект. Фоновая задача может быть принята до вычисления размера результата: тогда она сохраняет `failed` с этой причиной и без result ID. Создайте другой проект для нового импорта. Исходные журналы не удаляются автоматически. Старые данные читаются без уменьшения; отдельный верхний бюджет допускает служебное завершение уже принятых задач. Разбиение хранения по журналам вместо одного документа проекта остаётся следующим этапом.

Подтверждённая отмена сразу становится `cancelled`: terminal snapshot сохраняется до ответа и публикации браузеру. Работа парсера может некоторое время продолжаться, но уже не может опубликовать результат. Обычная ошибка обработки также сохраняется до публикации `failed`; результат и `completed` записываются вместе. При отказе записи неподтверждённое terminal-состояние не выдаётся за сохранённое.

После аварии сохранённые `queued`/`running` получают `failed` с причиной `interrupted` и без result ID. Автоматического повторного выполнения нет: исходный файл нужно загрузить снова. Уже сохранённые terminal jobs при повторном старте не меняют revision или результат. Восстановление выполняется отдельно для каждого проекта; атомарность старта всех проектов одновременно не заявляется.

## Первая настройка прервана

`setup-postgres.ps1` защищает `.local` ACL текущего пользователя и эксклюзивным bootstrap file lock. Credentials помещаются в приватный pending config **до** initdb. Пустой data directory с matching pending config может продолжить initdb с теми же паролями. Инициализированный PG18 с matching pending config получает атомарно записанный server config и атомарное завершение private config; повторный запуск не придумывает новые credentials.

Если initdb оставил неполный непустой directory, отсутствует соответствующий config или повреждён staging, запуск откажет с сохранением файлов. Восстановите совпадающий private config/backup в отдельное место и изучите приватные журналы; не удаляйте каталог ради повторной инициализации. Другой port или версия data directory также отклоняется. Поддерживаемая автоматическая recovery ограничена распознанными состояниями, не произвольным восстановлением потерянных secrets.

## Сбой во время работы

Session-local ограничения: connection 5s, statement 5s, lock 2s, transaction 10s, caller response 15s; queue64 с отказом при заполнении. Это предел отдельных вызовов, не всех многошаговых HTTP сценариев или общего потребления памяти. При истёкшем SQL/response deadline либо потере соединения экземпляр failclosed до перезапуска. Он не переподключается и не повторяет mutation автоматически. Ответ «изменение не подтверждено» не утверждает rollback: при потере commit acknowledgement возможна полностью сохранённая операция. После явного reopen сверяйте durable exports перед повтором.

Запись нескольких документов через batch атомарна. Восстановление interrupted jobs выполняется идемпотентно по проекту: queued/running становится failed/interrupted без result_id. При повторном запуске terminal revision не меняется. Startup всех проектов целиком не является одной транзакцией: при прерывании следующий запуск продолжает оставшиеся проекты.

Фактическую приёмку и границы каждого fault сценария фиксирует отчёт спринта; исходный код и эта инструкция сами по себе не подтверждают успешное восстановление.

При старте проверяются все сохранённые документы. Это пока полный read/typed round trip внутри ограниченной SQL-транзакции, а не масштабируемый каталог хранения. На debug-сборке независимый сценарий с примерно 153 MB накопленных документов реально превысил transaction timeout; исходные документы сохранились. Проверка оптимизированной Windows-поставки на той же базе ведётся отдельно. Прохождение одного размера не доказывает поддержку максимума всех проектов/журналов. Тайм-ауты не увеличиваются ради успешной проверки; оптимизация структуры хранения и проверки остаётся эксплуатационным долгом.
