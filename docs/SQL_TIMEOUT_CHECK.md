# Проверка SQL-тайм-аута, 11 октября 2026

Лимит PostgreSQL **5 секунд работает** с точными настройками из `src/cleanup.rs`. Проверено отдельно от законченного отчёта Sprint09; прежние голоса и решение не переписывались.

На новой пустой диагностической базе запрос `SELECT pg_sleep(8)` прерван через **5003,590 мс** с настоящей серверной ошибкой `57014: canceling statement due to statement timeout`. Следующий запрос получил `25P02`, затем `ROLLBACK` восстановил работу того же backend 45384. До и после в public было ноль объектов. Watchdog не сработал.

Неизменный Windows CLI 0.7.1 также проверен: тестовый loopback proxy добавил восьмисекундную задержку в первый запрос чтения идентичности базы. На wire зафиксированы реальные production startup options 5000/2000/10000 и backend 51888. Сервер вернул 57014 примерно через 5006 мс от наблюдаемого Parse; серверный журнал содержит тот же PID и точный тестовый запрос. CLI завершился с кодом 1 и `cleanup_storage_unavailable`, план очистки не создан. Watchdog не сработал. После ошибки сохранён ECONNRESET без предположения о причине.

После испытания отдельный запрос подтвердил: ноль объектов public, ноль соединений очистки, база доступна. Apply и DELETE не запускались. Создана только новая пустая диагностическая база; код продукта не менялся.

QA и TechnicalDebt независимо прочитали и сверили все 25 файлов доказательств. [Машиночитаемый результат и контрольные суммы](../flw/evidence/sql-timeout-diagnostic-2026-10-11.json).

**Это подтверждает настройку тайм-аута и обработку ошибки приложением. Исходный SQL5 на полном наборе данных остаётся INCONCLUSIVE_NOT_PASS:** тестовый запрос был намеренно изменён, поэтому он не заменяет приёмку исходной очистки. R3-01, R3-02, R3-04/DISK01 остаются OPEN, выпуск не разрешён.

Причина отсутствия тайм-аута в прежнем испытании с паузой чтения сети не установлена. Его успешное завершение не доказывает неисправность самого лимита.
