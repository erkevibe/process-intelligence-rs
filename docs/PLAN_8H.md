# Защита плана первого приближения за 8 часов

За 8 часов предлагается построить локальное приложение, которое принимает XES, показывает статистику и варианты трасс, строит DFG и обновляет карту после изменения порога. Это законченный пользовательский сценарий для проверки Rust + Datastar. Подтверждённая замена всего Apromore требует следующих этапов.

## Что пользователь получит

Публичный код, воспроизводимый запуск, небольшой демонстрационный журнал, проверенные ожидаемые результаты, рабочий экран анализа, экспорт JSON и отчёт о пройденных критериях. Дополнительная цель — отмена фоновой задачи и связь выбранного case с графом.

До защиты публикуются только документы. Отсчёт 8 часов начинается с первой операции разработки после защиты плана. Время установок, загрузок, сборок и ожидания входит в эти 8 часов; выполнение нескольких работ одновременно не увеличивает бюджет. В отчёте указываются начало, конец и фактические затраты. При обязательной пользовательской паузе фиксируются обе шкалы: календарная и активная.

## Что сокращаем при задержке

К 0:45 требуется рабочая сборка и определённый путь запуска. Если локальная установка затруднена, используется проверенный build в CI с исполняемым артефактом. Если ни один путь не работает, статус R1 — blocked by environment, а не «готово» по наличию исходников.

К 2:30 должен работать импорт, к 3:30 — вычисления, к 5:30 — интерактивный граф. При задержке сначала убираются T08 и дополнительные визуальные улучшения. Затем доступный бюджет идёт на T09/T10 и устранение ошибок базового сценария.

Rust4PM integration получает не более 45 минут диагностики несовместимого API внутри T04. Если требуется другой парсер, реализуется только ограниченный XES-subset из ТЗ через XML-библиотеку; DTD отклоняется. Такой fallback документируется и не выдаётся за проверку Rust4PM. Datastar CSP и базовый SSE остаются критериями выбранной архитектуры: их провал даёт частичный результат, а не скрытую замену стека.

## Почему именно такой объём

Импорт и DFG дадут полезный результат даже при переносе дополнительных сценариев. Маленькие ручные fixtures позволяют проверить смысл вычислений без работающего legacy. Граф и SSE проверят самое спорное архитектурное решение из переписки. Локальная память и один процесс сохранят время для этих проверок.

Полное восстановление legacy, PostgreSQL, Arrow/Parquet, S3, NATS, auth/RBAC, CSV, BPMN discovery/editing, Split Miner, conformance, calendars и обработка миллионов событий относятся к следующим этапам. Это границы обещания на 8 часов, а не отказ от долгосрочной цели.

## Проверка четырёх видов взаимодействия

| Сценарий из обсуждения | Приоритет | Проверка |
|---|---|---|
| Form validation | Обязательный | Upload и понятная ошибка на invalid XES |
| Interactive graph | Обязательный | Выбор node/edge, порог, сохранение pan/zoom |
| Long-running job | Дополнительный T08 | Реальный progress по этапам и cancel без позднего completed |
| Stateful multi-panel | Дополнительный T08 | Case details и graph selection согласованы после SSE |

Retain/remove activity не входят в R1: они требуют отдельной семантики фильтра и проверки. Отсутствие дополнительных сценариев не мешает сдаче базового прототипа, но Datastar baseline остаётся предварительным до полного spike.

## Применение FLW в пределах срока

Каждая T-задача получает hypothesis, expected effect, verifier, dependencies, cost/risk и evidence. Неудачные попытки сохраняются. Успешное решение становится локальной проверенной единицей только после реального выполнения; версия и область применимости обязательны.

Для T09 композиция import + mining + rendering проверяется отдельно. Прохождение отдельных тестов не подтверждает автоматически сквозной сценарий. Самообучающийся FLW runtime, mutation/search и перенос знаний между проектами в этот срок не разрабатываются.

## Сценарий защиты результата

1. Запустить приложение из опубликованной инструкции на чистом каталоге.
2. Загрузить fixture с известными 4 cases и 10 events.
3. Сверить частоты и варианты с ручной таблицей в ТЗ.
4. Выбрать ребро и изменить минимальную частоту с 1 на 2.
5. Убедиться, что A→C исчезло, а A→B и B→C остались; исходная статистика не изменилась.
6. Экспортировать JSON и сверить значения с экраном.
7. Загрузить повреждённый журнал и показать ошибку без потери предыдущего анализа.
8. Показать отчёт тестов, CSP, фактические лимиты и статус legacy compatibility.
9. При готовности T08 показать progress/cancel и case panel.

План защищается перед началом разработки по прямому условию пользователя. Технические разрешения на создание публичного репозитория и работу уже даны; дополнительных подтверждений обычных операций не требуется.
